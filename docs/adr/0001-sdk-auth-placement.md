# ADR-0001: SDK authentication mechanism placement (opi-ai vs Reference Product)

- **Status:** Accepted — recorded 2026-10-17 by Phase 20 task 20.1 (DEL-01).
- **Nature:** This ADR records a placement already selected by the registered Phase 20 delivery source ([spec-draft.md](../research/pi-ai-opi-ai-alignment/spec-draft.md)). It introduces no requirement, changes no runtime behavior, and marks no acceptance criterion met.
- **Gated tasks:** 20.18 (lazy AuthContext, default sources and management outcomes), 20.22 (store-owned mutation ACK, rotation, barrier and host bridge), 20.23+ (per-flow SDK OAuth migration, Anthropic first, then the remaining families).
- **Authority:** [opi-spec.md §8.2 “Product and independence admission”](../opi-spec.md) — cross-layer movement requires an ADR, and the placement case records ownership, dependencies, consumers, interface, conformance, authority, failure behavior, lifecycle, deletion test and migration.

## Context

1. The Phase 20 target is an independently usable `opi-ai` with SDK-reachable authentication: AIR-023 (reusable SigV4/Bearer/profile/default-chain sources independent of the coding agent), AIR-046 (construction and management contract with zero construction I/O), AIR-051 (all nine OAuth families with login/resolve/refresh), AIR-063 (store-owned serialized mutation/ACK and the credential mutation barrier); acceptance designs V-09/V-39/V-43/V-55.
2. Current placement at Opi HEAD `96b9709`:
   - `crates/opi-ai/src/auth.rs` owns only product-neutral value types and injection traits (`ResolvedAuth`/`AuthScheme`, `AuthResolver`, `OAuthCredential`/`OAuthLoginMethod`, `OAuthProvider`, `LoginPresenter`).
   - The Reference Product (`crates/opi-coding-agent`) owns every concrete mechanism: three OAuth flow implementations (`AnthropicOAuthProvider`, `CodexOAuthProvider`, `CopilotOAuthProvider`) plus `OAuthProviderRegistry` and `login_oauth` in `src/oauth.rs`; the OS-keychain store (`KeychainCredentialStore` over `keyring-core` with platform-native stores, service `opi`, presence service `opi.presence`); the cross-process serialization policy (one exclusive `fs4` advisory lock at `<user_config_dir>/credential.lock` wrapping write/delete/refresh, with bounded lock-held refresh HTTP); `CredentialResolver` (keychain-first with env fallback for API keys); the terminal presenter (`src/interactive_auth.rs`, calling `oauth::login_oauth` through `opi_ai::auth::LoginPresenter`); and wiring through `provider_factory`'s `ProviderBundle` (`store`, `resolver`, `OAuthProviderRegistry`) plus harness/`main` injection.
   - Current consumers: the Reference Product factory/harness//login paths above; `opi-agent` consumes per-call frozen resolved auth through `opi-ai` providers; product suites (`tests/oauth_auth.rs`, `tests/*credential*`) pin secret-canary, locking and acknowledgement behavior that must survive migration.
3. Gap versus the pinned Pi 1.3.0 snapshot: six of nine OAuth families are absent; the store transaction lacks the SDK contract (serialized modify with credential+metadata acknowledgement before success, `credential_mutation_barrier` cutoff/receipt capture, honest pending/unknown outcomes, late-write fencing, no default wait/receipt caps); the resolver lacks the 15-second network-refresh signal scope separated from lock and ACK, and the single Rust five-minute near-expiry correction with real stored expiry; construction must perform zero source I/O; a selected-source failure must never fall back to another account.

## Decision

1. **opi-ai (SDK layer) owns the product-neutral authentication mechanisms.** The per-flow OAuth protocol state machines for all nine families (browser/device/copy-code/manual paths, PKCE/state, exact token-exchange and refresh rules, flow metadata); source-selection precedence (typed per-call key > stored source > ambient; incomplete selected sources fail closed; HTTP 401/403 after a selected credential never restarts identity discovery); the injectable AuthContext/source/store/clock/transport seams; the store contract with serialized mutation, credential+metadata acknowledgement before success, and `credential_mutation_barrier` (synchronous same-store cutoff/receipt capture, no default wait deadline or receipt-count cap, honest pending/unknown reporting, late-write fencing); the single Rust five-minute near-expiry window over real service expiry; and the 15-second refresh network-signal scope that excludes store lock and persistence ACK. Construction and static reads perform zero env/store/auth/network work; failures are typed and redacted; there is no automatic browser, login, keychain or global runtime, and no account fallback.
2. **The Reference Product keeps policy and host adapters.** The terminal `LoginPresenter` implementation; OS-keychain persistence (`KeychainCredentialStore`, `keyring-core` plus platform-native stores, services `opi`/`opi.presence`); the `fs4` cross-process advisory-lock policy as the persistent store adapter's serialization boundary; product login/logout UX; config/credential-reference migration; and product wiring. These migrate to injected adapters behind the SDK contracts — they do not move into `opi-ai`.
3. **Real consumers.** The Reference Product bundle/resolver/login paths above; `opi-agent`'s per-call frozen auth through `opi-ai` providers; and the planned workspace-external consumer (AIR-050/V-42) that must log in and refresh using `opi-ai` alone with no Opi runtime dependency. Existing product suites are migrating consumers; their secret-canary, locking and acknowledgement assertions are retained.
4. **Minimal authority and dependency direction.** `opi-ai` gains no `keyring-core`, `fs4` or other native dependency from this placement; dependencies remain one-way `opi-coding-agent → opi-ai`. The SDK store contract is object-safe and injectable with a default memory store. No construction-time discovery, no permission/I/O/platform/supply-chain expansion for optional behavior. Deletion test: product auth policy stays replaceable at the injected presenter/store adapters; the SDK mechanisms are removable only together with their AIR/V obligations.
5. **Dependency and native maintenance costs.** SDK OAuth/SigV4/ADC mechanisms ride the Phase 20 selected backends (`reqwest` 0.12.28 + `Hyper` 1.9.0 H1 correction; `rustls` 0.23.40/`ring` 0.17.14; private OpenSSL 3 `LibCtx` EVP for ADC RS256/signing/KX; Smithy Query/XML 0.62.1, `xmlparser` 0.13.5, `p256` 0.13.2, `sha1` 0.10.6). Patch provenance, native/unsafe review and platform burden stay with those backend groups and their acceptance; this placement adds none. `keyring-core`, `fs4` and platform-native keyring stores remain product-side, so the movement adds no new native or supply-chain surface to `opi-ai`. No new crate is created.
6. **Reversible cutover.** Gated order 20.18 → 20.22 → 20.23+ (then the remaining flow families). Each task is one compiling, reversible slice; the product bridge migrates under the registered bounded order (validate destination conflicts → copy the explicitly chosen credential/reference → obtain destination acknowledgement → switch current consumers → retain the source until acknowledged finalization; never merge accounts or overwrite a different identity). Rollback is reverting the task slice before activation; a shipped rollback needs explicit release authority. No permanent parallel facade, duplicate SDK resolver or root-consumer patch survives the migration (AIR-021/AIR-045 exit proofs).

## Consequences

- Tasks 20.18/20.22/20.23 implement against this placement. Any interface drift, new host dependency, or second authority seam returns to placement review under the §8.2 triggers.
- `opi-ai`'s public auth surface grows (Models management outcomes, store and mutation-barrier contracts, flow APIs); scoped 0.x breaks synchronize the Unreleased changelog, callers, tests and bilingual crate docs.
- The product's current three flows are replaced by SDK mechanisms with injected UI/keychain adapters; their duplicated protocol code exits only after equal-or-stronger public-path proof (V-43/V-55).
- Recording this decision does not implement anything: runtime acceptance stays open until the owning tasks deliver evidence against the sole acceptance matrix.
