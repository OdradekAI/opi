## Comments

2026-11-06 首轮建议，尚未选择替换任何 backend。

保留“内部拥有明确边界、可单独验证、将来有条件拆出”的方向，但以能力和契约命名模块，不把 npm 包名逐一移植成 Rust 子模块。采用顺序建议：现有成熟 crate → 薄适配 → 对已证实缺口局部补足 → 有维护预算与差分证据的最小自研。

每个候选建立：必需行为、参考依赖版本、Rust 候选版本、缺口反例、封装成本、资源/安全责任、替换后的同一契约套件。官方 SDK 不存在与行为不匹配是不同问题；官方 SDK 存在也不意味着默认 auth/retry/hook 行为兼容。

本地 WebSocket 已有 PMD、Close、取消、源限定 TLS/代理等状态机；不得凭一个候选能连通就删除。HTTP 当前已复用 reqwest；AWS 官方 SDK 的存在需要重审旧的“无 SDK”前提，但不直接推翻当前签名/凭据实现。

同时必须反向核验旧自研边界：当前快照 Codex 的 getWebSocketConstructor 选择 Bun/globalThis.WebSocket；ai manifest 与 src 未找到 npm ws 依赖/导入。此调用点未显式配置 permessage-deflate，不能仅凭 opi 已实现 PMD 就把它升格为当前 Pi 的必需契约。先确认宿主实际行为和支持范围，再分别标出上游兼容、opi 既有承诺、新增工程要求；只有在 PMD 确属保留要求时，候选缺失 PMD 才构成拒用依据。

未来拆成独立 crate 的条件：出现真实独立消费者、稳定且无 opi 业务类型的接口、可以独立运行的契约套件，以及明确维护/发布收益。现在无需为了潜在拆分增加公共接口或通用 plugin 框架。

### 继续讨论：按能力划分依赖边界

2026-11-06，telemetry 的边界与生命周期政策已确认。本票成为下一项设计前沿；以下是待确认的选型策略，不是依赖替换计划或编译通过结论。

建议采用“能力模块 + 依赖实现 + 契约适配”的结构。模块可以独立测试而保持 crate 内私有，不需要为了测试成为 public，也不需要按 JS 包名复制一套 Rust 包。只有实际扩展消费者需要的接口才进入公共面。

| 能力 | 现阶段建议 | opi 必须拥有的适配语义 |
| --- | --- | --- |
| HTTP/TLS/代理连接 | 保留现有 reqwest/rustls 复用；不借结构重整自动升级版本或重写通用连接机制 | 显式/scoped 配置、代理和信任策略、headers、timeout、取消与错误体的入口规则 |
| WebSocket | 先保留可验证的现有实现，把连接/握手、codec、Codex session/fallback 的责任分开；候选通过合同后再替换 | 目标宿主行为、握手/代理/TLS、控制帧、取消和关闭、错误映射；PMD 是否必需必须先有基准证据 |
| AWS 能力 | 评估官方完整 SDK；有明确模型/回调边界缺口时评估官方签名/eventstream 等组件，再决定需保留的本地机制 | 凭据来源优先级、Pi 请求/事件/错误转换、异步 hooks、strict fallback 与重试次数；不直接继承默认链为兼容结论 |
| SSE 与增量解码 | 相同词法规则经 fixture 证明后复用；协议事件/终止规则保留在各 API adapter | 字节切分、UTF-8/CRLF、多 data 行、EOF，以及协议专属终态和后续 usage |
| Provider/协议语义 | 作为 opi 自有业务适配层维护；使用 SDK 仍需这层 | Model/Message/Options、tool/reasoning、事件次序、usage、错误阶段、会话与回放 |

这里的“保留现有”是迁移顺序，既不代表已通过 Pi 1.5.0 验收，也不将旧私有实现细节自动升级为目标。源码搬迁与行为替换应分别可验证；实现进入生产前仍须满足验收。

#### 自研机制的准入

具体依赖决策记录以下证据即可，不另建庞大的流程：

- 对应的上游能力/入口及固定版本。
- 候选 Rust 依赖及公开扩展点。
- 同一输入/时序下的请求、事件、错误、状态和清理结果。
- 不能由公开 API 或有限适配满足的具体反例；一般的“没有官方 SDK”“库不够灵活”不构成已证实缺口。
- 自有代码因此必须承担的最小机制，以及未来可替换的条件。

优先顺序建议为：成熟依赖直接复用 → 薄适配 → 局部补足 → 有证据的最小自研。如果“薄适配”需要访问私有状态、复制整个 parser 或长期 fork 状态机，就按自研维护成本评估，不能仍称薄封装。

#### 模块和公共面的边界

- 底层 backend/codec/签名细节默认私有；稳定公共面承载用户真正需要的 provider/API 扩展、配置和已承诺的协议能力。
- 不为了将来可替换每个库引入一个 trait；已经需要生产/测试替身或多种实现的职责才设替换接口。现有真实 seam 可继续复用。
- 保留独立的模块契约与原始 fixtures，既能验证当前实现，也能作为候选替换的准入标准；测试驱动不能复用被检验的转换逻辑生成 expected。
- 公共协议专用能力按映射保留，不能用“内部默认私有”删除原本的对外能力。
- 出现真实独立消费者、可独立验证的接口与明确维护收益后，再讨论独立 crate/发布身份；不提前冻结底层公共 API。

#### 与已确认生命周期的衔接

provider/transport adapter 的 channel-closed 或临时 read future Drop 不能越权替代逻辑请求的取消策略。请求层持有生产执行直到终态/已声明取消条件；底层只负责执行收到的取消与清理职责。更换 SDK/WS backend 时也必须覆盖“用户不消费/释放消费句柄但请求继续”的轨迹，不能因为候选库默认随对象 Drop 关闭就悄悄改变合同。

#### 用户已确认的策略（保留原问题）

是否采用：以能力组织内部模块，优先复用成熟依赖；自研需有具体不可兼容证据；底层默认私有；现有实现与候选先跑同一契约，再决定替换？

推荐采用。这保留独立测试与排查边界，也允许有充分依据的局部自研。它不代表已经选定 WebSocket/AWS 的具体候选、关闭 PMD 支持或批准任何依赖升级。

## Answer

2026-11-06 用户回复“同意，继续推进”，确认：按能力封装内部模块，成熟依赖优先；自研须有具体不兼容证据；底层默认私有；当前实现与候选通过同一契约验证后再决定替换。

确定的选型规则是“直接复用 → 薄适配 → 局部补足 → 有证据的最小自研”。保留独立测试、定点排查和未来有条件拆 crate 的能力；模块的存在不意味着必须重写其底层依赖，也不意味着需要公共 codec/签名接口。

库提供机制，opi 保留 Pi 所需的请求、事件、错误、凭据、回调与生命周期语义。不得让依赖默认值或 receiver-closed/Drop 行为覆盖已确认的请求执行与消费分离合同。长期 fork/访问私有状态/复制状态机按自研成本评估。

该决策不选定具体 WS/AWS 候选，不批准依赖升级、删除现有实现或取消 PMD 支持。具体实现替换需记录固定版本、必要契约、缺口反例、同一契约结果与维护收益；尚无结果的候选不能写成已适配。

模块结构可据此继续设计：声明稳定职责和依赖方向，为通过契约的实现保留替换位置，不以特定候选的内部类型决定通用消息或模型类型。具体版本和功能组合验收由后续验收决策承接。
