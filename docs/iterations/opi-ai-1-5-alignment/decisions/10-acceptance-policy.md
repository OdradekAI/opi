## Question

如何把给定 pi-ai Rust 验收文档转化为可执行契约清单：冻结哪些基准，如何分别判定行为等价、Rust 工程质量、资源安全和交付？哪些条目是上游兼容事实、哪些是新增工程预算；如何表达阶段性通过而不稀释最终完整对齐承诺？

## Comments

2026-11-06 首轮建议，尚未修改用户提供的验收标准。

保留原标准“四者不可抵消”的原则及六类发布门：范围、行为、结构、测试、运行、交付。先迁移到用户指定快照的真实源码与测试分母，再生成契约清单；不能沿用旧 commit 的 185 个测试或旧行为而把快照误判。

区分两层要求：一层是上游兼容事实（请求、事件、错误、状态、副作用等）；另一层是新增工程要求（fuzz 执行预算、资源耐久次数、p95/p99 阈值、平台组合）。新工程预算需要在候选执行前冻结；建议变更时新建规范版本，保留原值和理由，不在失败后回调标准。

执行分为开发快速检查、合并/集成检查和本次完整对齐里程碑的全门禁；后续普通发布按影响补证。分层改变执行频率，不改变所声明结论的适用门槛。阶段成果可写“独立接入通过”或“指定协议对齐通过”，不写“完整 pi-ai 复刻通过”。跳过、受阻、未运行、有意差异分别列出。

将主契约矩阵作为验收证据的索引，避免每项标准生成一个独立测试：ID、来源、Rust 入口、输入/时序、判等规则、主要测试、原版录制、结果/环境、差异。一个案例可以证明多个相关契约；多层测试也可共同证明同一高风险契约。

重点风险：Rust 与 JS 引用/惰性/异常语义；上游缺陷与安全修正冲突；全量能力与最小构建并存；实际包的外部消费；可控服务响应与真实 LLM 非确定输出分离。有限测试和覆盖率不能证明任意未来输入严格等价。

#### 采用原标准，先修正基准归属

建议保留原文的四项共同要求：完整能力、可观察行为等价、Rust 工程合格、证据可复现，以及范围/行为/结构/测试/运行/交付六门。迁移时保留原条款族 ID，逐项标记沿用、按快照改写、拆分或新增，不能只摘出容易通过的项目另成一套低标准。

#### 范围和结论的表达

验收范围按原公开能力展开，除聊天外包含图像、分类、deferred 能力判断、Faux、认证与 OAuth、目录/费用、工具/schema、transcript、公开辅助函数、compat、可达协议入口及必要宿主能力。原包的 pi-ai CLI 和目录生成/校验工具仍有单独映射项；独立库调用不要求安装 CLI，与验收这些包级能力并不冲突。可用可选薄命令/工具承载，核心不得依赖产品 CLI；不能以 Rust 是 library 为由静默漏掉完整包范围。

本轮 opi-telemetry 只验收[已确认的中立范围](05-telemetry-boundary.md)，覆盖 AI 所需 context/span、schema、metrics、no-op、记录与适配合同；不扩大成完整 pi-telemetry Store/query/render 或 Durable/Chord 实现。依赖包中经 pi-ai 暴露的行为仍计入 AI 合同，依赖包自身无关功能不因此纳入。

结论按下列方式分开报告，不使用加权总分：

- **范围限定通过**：如“打包后的核心＋Faux 独立接入通过”或“指定 Responses 协议与配置通过”。列出准确范围、缺口和证据；不能简称完整对齐通过。
- **行为严格对齐通过**：固定输入/平台范围内全部适用行为契约有证据，零未解决差异、零有意差异计入通过。它不能抵消工程、资源或交付失败。
- **完整验收通过**：最终完整范围内六门全部通过；适用的必须执行项没有失败、未执行或受阻。有限验证仍不意味着任意未来输入都得到数学证明。
- **包含已批准差异的交付**：明确列出差异及兼容范围；其工程/交付门可独立通过，严格等价结论不能给它补绿。未批准差异继续阻断对应契约。
- **当前真实服务可用**：仅对有 L8 记录的 endpoint/model/auth/候选版本声明，另标日期；不能推导未调用服务也可用。

每个契约仍使用通过、失败、未执行、受阻、不适用、有意差异六种明确状态。真正不适用需有来源/能力/平台理由；某个最小配置关闭能力，只影响该配置适用行，不从总体完整能力清单删除该能力。skip、超时、工具缺失和数据缺失不得算通过。

#### 单一契约索引与差异规则

复用一份契约索引，原文 B/C/D/E/P/A/M/U/X/G/R/T/S/Q/K 等编号作为来源族。具体行按入口和观察面细化，关联已有用例，而不是每条标准新建一组重复测试。最少字段为：

```text
contract_id / source_identity / source_entry / source_clause
rust_entry / profile / preconditions / input / actions_and_schedule
observations / equality_rule / primary_test / complementary_test
oracle_record / rust_record / environment_and_artifact_hashes
status / difference_or_blocker / replacement_mapping
```

源码、旧测试、README 或运行结果冲突时，将该契约单列；不能按“源码总是对”或“文档总是对”一刀切。发生有意变化时记录原因、影响的调用者、范围和已批准决策；旧 RDF/AIR 的接受记录不能自动批准本轮严格对齐下的例外。

判等尤其保留如下信息：缺失/null/默认值、UTF-16 单位、浮点分支、header 覆盖、原错误载体、partial 的延后读取与别名关系、请求次数/顺序、Store 已发生写入与内存发布。比较器必须通过负例，不能靠删字段、全局排序、复制活对象、只拼最终文本或自动重跑变绿消除差异。

例：保留 start.partial 后继续推送内容，再读取已保留值，是一个独立观察动作。Rust 换成不可变快照若改变结果，就是差异；安全 Rust 可以选择不同的数据表达，但“Rust 原生”不授权删掉这项观察。若保留行为与工程约束无法同时满足，回到有意差异决策，不在实现中私自放宽 expected。

同理，observer 抛错造成原版 pending/unhandled rejection 的路径分别记录业务结果、遥测状态与宿主错误通道，在有界窗口内观察并通过测试宿主清理。修正该路径可能满足工程门而产生兼容差异，两份结果同时保留；既不让测试无限挂住，也不把原版缺陷当作资源门豁免。

#### 配置和平台：冻结有限集合 V

最小配置须支持核心＋Faux，排除可选网络 backend、云认证 SDK、内嵌目录与具体遥测适配；这项独立接入要求已确认。最小不是零依赖，也不自动要求 Tokio-free。**提供最小配置不等于默认配置必须最小。**

2026-11-07 此前曾建议默认核心＋Faux，但用户追问 Pi 的真实默认策略后重新核对了上游，证据见[默认能力与入口加载核查](../evidence/default-configuration.md)。Pi 普通安装声明完整 SDK 依赖，根入口轻量，createModels 为空集合，builtinModels 显式注册全部内置 provider；README 首例使用 builtinModels。原来的默认核心建议是成本取舍，并非上游策略或已确认决定。

据此撤回“默认核心＋Faux”为首选的建议，改为推荐：**默认具备支持平台上的完整内置模型调用能力，同时提供 default-features=false 的最小/定制构建；运行时注册仍显式。** 包括内置协议/provider、目录和必要认证能力，不等于开启所有可选 tracing 适配、exporter、CLI、测试设施或互斥平台后端。普通 Models 构造为空；单 provider 注册与显式全内置构造并存。README 单 provider 首例与这一默认安装策略相容。

默认完整会带来更多依赖构建成本，不能用运行时 lazy 初始化宣称编译成本消失。按需初始化客户端/凭据/连接的时点仍逐入口验收；无请求不自动联网、登录或启动 exporter。此默认策略已由用户确认，见 Answer；尚未修改 Cargo，总能力验收覆盖全部目标操作。

V 的每行要记录 OS 版本/架构、runner 镜像、Rust 工具链/MSRV、Tokio 模式、features、依赖解析与命令。配置族至少覆盖：

1. no-default、default、核心＋Faux 的外部包调用。
2. 每个独立可选能力及其必要依赖；每种协议/云认证/目录/遥测适配有实际启用证据。
3. 各兼容能力组的全开配置、有效两两组合，以及已知多能力风险组合：例如代理＋TLS＋WS、OAuth 刷新＋Store 提交＋取消、provider 切换＋session 缓存、spawned producer＋telemetry。
4. 至少一个覆盖全部纳入范围能力的主配置。all-features 只有在该组合本身被支持时才是有效行；不能代替前述配置。

沿用仓库 major milestone 的三 OS 原生回归要求，建议将用户实际 Windows 目标作为主验收配置，执行完整 L1–L7 和 S/Q；Linux、macOS 执行原生产品回归及各 V 行适用的入口、序列化、取消/资源、代理/凭据、CLI 和外部包消费。平台敏感行为补该平台原版对照。T04 的 feature 组合要求按适用平台展开，不只在一个 OS 上测试 feature 再推导其余平台通过。

现有 scripts/opi-ci-scope.py:13 只选 *-latest runner，platform-verify.yml:92 的 full 是产品 workspace 回归，:100 的 opi-ai smoke 只是 auth_process_lifecycle。release.yml:31 起的六目标是 opi-coding-agent 二进制构建，部分为交叉编译，Windows ARM64 还允许构建失败；它们不等于 opi-ai 六架构原生验证。其他架构分别标原生验证、仅编译、允许但未验证或不支持。原生目标、镜像与工具链精确值在运行前写入 V，禁止只留 latest 标签作为最终身份。

MSRV 先以当前声明 1.97 为目标，最终工具链版本与依赖闭包在候选验证前冻结。新增依赖要求提高 MSRV 或增加宿主要求时，须显式评估与更新支持范围；不能在 README 中保持旧承诺。JS 浏览器绑定未纳入；Pi 的云 binding/宿主能力仍需 Rust 映射和明确支持条件，不能用“非 JS”漏掉功能。

#### 数值门槛：本次完整对齐里程碑的候选预算

兼容事实和新增工程要求分别标注。下表摘要不替代原文的完整条件；此前建议保留原数值作为本次里程碑门槛，具体预算仍待确认。行为完整性与不伪报通过的要求不随测试频率降低；30 CPU 分钟、10000 次及性能倍率等工程数值需要先明确适用目标、负载、测量方法与预计成本。必要时进行明确标为校准的试跑，保留原始结果，再在正式候选验收前确认预算；校准不是已通过验收。当前没有性能数据可以证明通过，也不应把原建议当作已批准要求。

| T05 分片 | 典型合法/malformed 短样本 ≤4096 字节：所有二分切点及单字节切分；长样本至少 100 个固定种子多段切分 |
| T06/T09 交错与覆盖 | 每个有状态职责至少两个并发调用、两个独立身份及已枚举屏障顺序；冻结的适用契约、状态迁移、回归族 100% 有断言，具名非等价关键 mutation 全部被检出 |
| T07 fuzz/属性 | 每个适用 fuzz 目标至少 30 CPU 分钟；相关属性族至少 10000 个有效生成案例，记录语料/种子/输入深度/超时等身份 |
| T10 原版录制 | 每个差分案例在固定输入/时序下重复 TS 至少 3 次；有非确定性时登记有证据的允许结果集合，失败不靠重试刷绿 |
| S01/S04/S05 | 未授权位置合成 secret 命中 0；完成必需提交与清理后资源回基线或声明的缓存容量/TTL；正常/错误/取消/停止消费/全不消费各 10000 次生命周期，覆盖并发 1/8/32 |
| Q05 延迟/CPU/吞吐 | 可比较负载中，Rust÷TS 的 p95/p99 延迟与 CPU/请求单侧 95% 置信上限 ≤1.10；吞吐倍率单侧 95% 置信下限 ≥0.90，逐路径判定 |
| Q05 冷启动/RSS/目录 | 冷启动及峰值 RSS 倍率的单侧 95% 置信上限 ≤1.10；目录按 10 provider×100 model 的成功/失败/挂起场景及原文门槛执行 |
| 长工具参数回归 | 25000/250000 字符、32 字符切片；累计分配 large/small<25，large 分配字节/实际 JSON 文本长度<5000。该阈值需保留源回归来源，不能仅测存活堆 |
| 普通取消至清理 | 无必须继续提交的路径，Rust p99≤max(TS p99×1.10,100ms)，单次≤1000ms；OAuth 轮换等另按声明提交/超时规则 |
| L8 当前可用声明 | 对被声明的集成保留候选版本在发布前 7 日内的真实 endpoint/model/auth 成功记录；没有凭据或调用失败即不能声称该项当前可用 |

对应的候选测量方案沿用原文：预热 5 批、交替至少 30 配对批次、延迟每批至少 1000 操作、冷启动 30 个独立进程；时长不足 100 个时钟分辨单位时聚合后重测。这些次数与门槛一并校准确认，不是已批准的固定运行量。正式运行前登记计时范围、分配计数口径、配对单位、置信区间方法、输出保留策略和环境；正确轨迹先通过，才有可比较的性能结果。置信区间跨已冻结阈值、无法统一计数范围、工具缺失或样本不足都属于证据不足，不自动通过。

fuzz 目标按自有不可信输入边界和实际适配责任建清单，不把每个依赖函数都新建一套 fuzz，也不能通过合并名字漏掉独立攻击面。已被依赖替换的私有实现按测试替代规则退役，新 backend 的包装/配置与外部契约仍须覆盖。S05 的数量按原文“每场景”口径记录，并明确每种并发和各独立状态所有者的覆盖，避免把全不消费改成偷偷消费或丢事件以通过。

“停止消费后继续执行”意味着释放 consumer 并不是 S04 资源回基线的起点；必须等待请求自身终结及必需提交完成。执行期允许的事件队列增长按冻结负载与原合同观察；不能一方面保持无限输入/全不消费，一方面虚构固定内存上限。申请取消与 cleanup 已完成也要分别计时。

这些是本次建立完整基线时的候选要求，不是每次提交或普通发版的运行量。预算正式冻结后，若事实说明某指标测量不可比或预算需改变，应先形成新规范版本、保留旧值/结果/理由并重新确认，不得在已有失败后覆盖原 expected 或降低门槛冒充通过。
