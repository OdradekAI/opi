## 维度

### 1. Provider 抽象、集合/Models、registry、工厂和分派

**opi：** opi-ai 定义了仅支持流式处理的 `Provider` trait，并为每个 Provider 提供 `ModelInfo` 目录；其上分层设置了 `ProviderRegistry`（规格解析 + 模型覆盖）和 `ProviderCollection` facade（认证描述符、兼容性元数据、stream/complete 分派）。`provider_factory.rs` 是唯一的集中构建位置。内置九个 Provider；可通过 TOML 定义 OpenAI 兼容的自定义配置档；还可通过 opi-agent 接入 extension 提供的 Provider。关键事实：

- `Provider` trait 仅包含 `id`/`models`/`stream`——`crates/opi-ai/src/provider.rs:12-23`
- `ModelInfo` 包含 7 个字段（无成本、headers 或思考级别映射）——`provider.rs:64-73`
- `ProviderRegistry` 解析 `'provider:model'` 字符串规格——`crates/opi-ai/src/registry.rs:117-293, 302-314`
- 单一集中式工厂覆盖 9 个 id——`crates/opi-coding-agent/src/provider_factory.rs:620-862, 236-246`
- `ProviderError` 有 9 个变体，并映射到 `ProviderErrorCategory`——`crates/opi-ai/src/provider.rs:124-218`
- `AuthDescriptor` 标记为 `#[non_exhaustive]`，且仅有 StaticApiKey/EnvApiKey/Resolved——`crates/opi-ai/src/provider_collection.rs:97-119`

**pi 0.80.2：** pi-ai 定义了 `Provider<TApi>` 接口（id/auth/getModels/可选 refreshModels/stream/streamSimple），以及具备认证解析和 stream/complete/streamSimple/completeSimple 分派能力的 `Models` 集合。`createProvider()` 是通用工厂；`builtinModels()` 注册了 ~35 个内置 Provider。认证是一套完整契约：每个 Provider 均可定义 ApiKeyAuth + OAuthAuth，配有 `CredentialStore`，并支持 env/环境凭据/OAuth 解析。模型携带成本、思考级别映射，以及每模型的 compat/headers。另有独立的 `ImagesModels` 接口面用于图像生成。关键事实：

- `Provider<TApi>` 泛型接口——`packages/ai/src/models.ts:32-72`
- `Model` 包含 13+ 个字段，包括 cost{4}、thinkingLevelMap、headers、compat——`packages/ai/src/types.ts:660-690`
- `createProvider` 是通用工厂，并对进行中的 refreshModels 去重——`models.ts:295-369`
- ~35 个内置 Provider 工厂——`packages/ai/src/providers/all.ts:70-108`
- `ApiKeyAuth` + `OAuthAuth` + `CredentialStore{read/modify/delete}`——`packages/ai/src/auth/types.ts:47-69, 129-182`
- `ImagesModels` + `generateImages`——`packages/ai/src/images-models.ts:12-87`

### 2. 凭据/认证模型

**opi：** 仅支持静态凭据/环境变量凭据，在启动时解析，且从不持久化或刷新。`AuthDescriptor`/`AuthStatus`/`SecretKey` 这一抽象接口描述凭据来源，并在诊断时对值脱敏。Bedrock 具有本地 config>env>profile-file>credential-process 链；Vertex 仅接受静态 token。关键事实：

- `AuthDescriptor` + 脱敏的 `SecretKey` newtype——`provider_collection.rs:54-84, 97-119`
- Bedrock 本地凭据链（config>env>INI>credential_process），不支持 IMDS/SSO/web-identity——`bedrock/credentials.rs:93-186, 142-144`
- Vertex 仅支持静态 `VERTEX_ACCESS_TOKEN` Bearer——`vertex.rs:213`、`provider_factory.rs:820-849`
- `opi doctor` 探测凭据是否存在（不读取值）——`doctor.rs:332-435, 602-688`
- 无 CredentialStore、无 OAuth、无 keychain（grep 搜索未返回匹配项）

**pi 0.80.2：** 提供完整的 `CredentialStore` 抽象，支持基于文件的持久化（`auth.json` 模式 0600、跨进程锁定）、不暴露值的状态检查、env/ADC 环境凭据检测，以及 Anthropic/Copilot/Codex 的完整 OAuth；token 刷新在 store 锁下执行。关键事实：

- `CredentialStore{read/modify/delete}` 按 Provider 串行化——`auth/types.ts:47-69`
- 基于文件的 `FileAuthStorageBackend`，使用 `proper-lockfile`——`coding-agent/src/core/auth-storage.ts:53-217`
- OAuth token 通过双重检查锁刷新——`auth/resolve.ts:86-120`
- Anthropic OAuth（auth-code + PKCE）、Copilot（device-code RFC 8628）、Codex（browser + device）——`utils/oauth/{anthropic,github-copilot,openai-codex}.ts`
- Vertex ADC 文件检测（`~/.config/gcloud/application_default_credentials.json`）——`providers/google-vertex.ts:6-28`
- Bedrock 环境凭据：bearer token/AWS_PROFILE/env keys/ECS task role/web-identity；签名委托给 AWS SDK——`providers/amazon-bedrock.ts:11-25`
- `AuthLoginCallbacks` 交互式 prompt/notify/device-code/manual-code——`auth/types.ts:92-123`

|---|---|---|---|

### 4. 流式处理/传输生命周期

**opi：** 采用统一的 `AssistantStreamEvent` 协议，每个 Provider 分别使用 reqwest 进行流式处理，并配有 `CancellationToken`。重试/退避位于 opi-agent 的 `agent_loop`（而非 Provider）中，通过手动指数退避循环实现；该循环在休眠期间也响应取消，并在已交付任何流内容后停止重试。代理位于 HttpClient 层，使用 `reqwest::Proxy`。缓存控制很少。关键事实：

- 12 变体的 `AssistantStreamEvent`——`crates/opi-ai/src/stream.rs:210-279`
- Agent 层使用 `RetryConfig` 重试，在产生部分输出后停止重试——`crates/opi-agent/src/agent_loop.rs:86-87, 125, 396-451`
- `parse_retry_after`（秒数 + IMF-fixdate + x-ratelimit-reset）——`crates/opi-ai/src/retry.rs:59-90`
- 在流 + 休眠中通过 `CancellationToken` 取消——`agent_loop.rs:128-140, 436-450`
- `reqwest::Proxy::all` 单一全局代理；环境变量 HTTPS_PROXY 优先——`crates/opi-ai/src/http.rs:122-153, 166-219`
- `CumulativeUsage` 聚合器——`stream.rs:89-172`
- 不发出 cache_control 标记；无会话亲和性 headers——grep 搜索未返回匹配项

**pi 0.80.2：** 结构相同的 `AssistantMessageEvent` 协议构建在泛型 `EventStream<T,R>` 之上。重试委托给 Provider SDK（由 `maxRetries` 和 `maxRetryDelayMs` 上限控制），没有 Agent 层重试循环；通过 `AbortSignal` 取消。代理按目标 URL 解析（仅 HTTP/HTTPS）。缓存控制丰富（Anthropic `cache_control` 标记 + 1h ttl、OpenAI `prompt_cache_key` + retention、会话亲和性 headers）。用量包含单独的 `cacheWrite1h` 和内联成本。关键事实：

- 相同的 12 变体事件联合类型——`packages/ai/src/types.ts:447-459`
- 没有 Agent 层重试；`streamAssistantResponse` 仅调用一次——`packages/agent/src/agent-loop.ts:275-368`
- 委托给 SDK 的重试 `maxRetries`/`maxRetryDelayMs`——`types.ts:161-172`
- 按目标解析代理 URL；拒绝 SOCKS/PAC——`utils/node-http-proxy.ts:69-112, 89-90`
- `streamProxy` 服务端流中继——`packages/agent/src/proxy.ts:116-233`
- Anthropic `cache_control` + 1h ttl——`api/anthropic-messages.ts:56-70`
- OpenAI `prompt_cache_key`（限制为 64）+ `prompt_cache_retention:'24h'`——`openai-completions.ts:548-553`
- 会话亲和性 headers——`openai-completions.ts:514-518`
- `OVERFLOW_PATTERNS` 正则表达式集合（覆盖 20+ 个 Provider）——`utils/overflow.ts:35-59`
- 自适应/脱敏/签名式思考——`anthropic-messages.ts:185-223, 578-587`

|---|---|---|---|

### 8. 内置工具集、模式感知策略与可插拔 Operations

**opi：** 八个受 workspace 范围约束的内置工具（read/write/edit/bash/grep/find/ls/glob）。采用集中式强类型 PathPolicy（WorkspaceOnly/AllowOutside），具备符号链接穿越检测和 Windows 原样路径前缀剥离能力。策略可感知模式：交互模式默认启用变更型工具；非交互模式默认为只读，并通过 `--allow-mutating` 控制变更型工具的启用。没有可插拔的 Operations 层；所有工具均硬编码依赖 tokio::fs/std::fs/ignore::WalkBuilder。变更操作的串行化粒度较粗，按轮次分批执行。各工具的加固措施较为全面。关键事实：

- 8 个工具，BUILTIN_TOOL_NAMES 包含 glob — `crates/opi-coding-agent/src/policy.rs:19-21`
- 模式感知默认值 CODING 与 READ_ONLY — `policy.rs:23-24, 69-74`
