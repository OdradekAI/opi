## 1. Provider abstraction & dispatch

**opi:** opi models providers as a streaming-only `Provider` trait (`id`/`models`/`stream`) implemented by eight concrete provider types plus a MockProvider and a non-dispatchable MetadataProvider, dispatched by a two-layer `ProviderRegistry` (resolve `provider:model` spec) wrapped by a `ProviderCollection` that adds auth-gated dispatch and OpenAI-compat metadata. A centralized `provider_factory.rs` builds the active provider plus all registered models from TOML config + env; the agent loop calls `provider.stream(request)` directly on an injected `Box<dyn Provider>` (the model id can change mid-run via `Agent::set_model`, but the provider object is fixed). There is no dynamic/async model discovery, no OAuth login, no `complete` trait method (complete dispatch drains the stream), no `streamSimple` variant, and no image-generation surface.

Key facts:
- `Provider` trait has three methods: `id()`, `models() -> &[ModelInfo]`, `stream(request: Request) -> EventStream`; no `complete`/`refresh`/auth methods on the trait. — `crates/opi-ai/src/provider.rs:12`
- `Request` is a flat struct (model, system, messages, tools, max_tokens, temperature, thinking, stop_sequences, metadata, cancel: CancellationToken); auth/baseUrl/headers are NOT in the request — they are baked into the concrete provider at construction. — `crates/opi-ai/src/provider.rs:30`
- `ProviderRegistry` resolves a `provider:model` string via `split_spec` (single colon, rejects empty halves), supports runtime `register_provider`/`register_model` overrides, and dedups overrides in `all_models()` for `--list-models`; no async, no fetch. — `crates/opi-ai/src/registry.rs:117`
- `ProviderCollection` wraps a `ProviderRegistry` and adds `AuthDescriptor` (StaticApiKey/EnvApiKey/Resolved), `CompatMetadata`, and `dispatch_stream`/`dispatch_complete`; complete dispatch (`dispatch_complete` at :359) drains the streaming trait (no separate complete method on `Provider`). — `crates/opi-ai/src/provider_collection.rs:245`
- `refresh()` is a documented no-op stub (`Ok(())`): no refresh behavior is implemented; there is no dynamic model-catalog fetch anywhere in opi-ai. — `crates/opi-ai/src/provider_collection.rs:374`
- Nine built-in provider ids are hard-coded (`BUILT_IN_PROVIDER_IDS`: anthropic, openai, openrouter, mistral, openai-responses, gemini, bedrock, azure, vertex); `build_runtime_provider` match-dispatches to per-provider constructors that read env vars / config and return `Box<dyn Provider>`. — `crates/opi-coding-agent/src/provider_factory.rs:236`
- `build_provider` selects ONE active provider from `config.defaults.model` (a single `provider:model` spec); the agent loop receives that single provider object — there is no per-request multi-provider routing at the loop layer (only same-provider model-id switching via `Agent::set_model`). — `crates/opi-coding-agent/src/provider_factory.rs:620`
- Custom providers are only OpenAI-Chat-compatible profiles (`OpenAiCompatibleProviderConfig` -> `OpenAiChatProvider::new_for_profile`); a non-OpenAI custom provider cannot be registered via config without writing Rust. — `crates/opi-coding-agent/src/config.rs:177`
- `CompatConfig` carries exactly 9 flags (system_role_override, max_tokens_field, tool_result_name_field, usage_in_stream, strict_tool_schema, reasoning_effort, cache_key, require_assistant_after_tool_result, chat_completions_path); `extra_headers` lives on the profile/provider, not CompatConfig. — `crates/opi-ai/src/openai_chat.rs:708`
- Dispatch to the wire is `context.provider.stream(request)` on `AgentLoopContext.provider: Box<dyn Provider>`; the collection/auth seam is bypassed on the live run path (harness uses MetadataProvider for listing only). — `crates/opi-agent/src/agent_loop.rs:118`
- Eight concrete `impl Provider for` types exist in opi-ai: AnthropicProvider, OpenAiChatProvider, OpenAiResponsesProvider, GeminiProvider, AzureOpenAIProvider, BedrockProvider, VertexProvider (plus MockProvider in test_support and MetadataProvider in provider_factory). No anthropic-cache_control/eager_input/adaptive/session-affinity handling exists in anthropic.rs. — `crates/opi-ai/src/anthropic.rs:1004`

**pi:** pi models providers as a data `Provider` object (`id`/`name`/`auth`/`getModels`/`stream`/`streamSimple`/optional `refreshModels`) built by a `createProvider` factory whose `api` field is a map keyed by `model.api` string, dispatching to lazy-loaded API implementation modules. A `Models` collection resolves auth per-request (api-key + OAuth with double-checked refresh locking), exposes four dispatch primitives (stream, complete, streamSimple, completeSimple), and 34 built-in provider factories ship in `providers/all.ts`; there is a separate image-generation registry (`ImagesModels`).

Key facts:
- `Provider<TApi>` interface: `id`, `name`, `baseUrl?`, `headers?`, `auth: ProviderAuth` (required), `getModels()`, optional async `refreshModels()`, plus both `stream` and `streamSimple`; auth is a first-class per-provider property, not a separate seam. — `packages/ai/src/models.ts:33`
- `createProvider` dispatches on `model.api` via an `api` field that is either a single `ProviderStreams` or `Partial<Record<TApi, ProviderStreams>>`; a model whose api has no entry yields a `ModelsError('stream')` — providers are api-multiplexed, not monolithic per backend. — `packages/ai/src/models.ts:324`
- `ModelsImpl.stream` wraps `lazyStream` around async auth resolution (`applyAuth` then `provider.stream`); auth is resolved per-request, not baked in at construction, and merges request options with resolved auth. — `packages/ai/src/models.ts:259`
- `ModelsImpl.refresh(provider?)` calls each provider's optional `refreshModels()` (concurrent allSettled across providers at models.ts:214; per-provider fan-out at models.ts:354-364); static providers without `refreshModels` are no-ops — dynamic model discovery is a first-class capability. — `packages/ai/src/models.ts:199`
- `resolveProviderAuth` handles stored OAuth credentials with double-checked refresh locking under `CredentialStore.modify` (resolveStoredOAuth at auth/resolve.ts:86), stored api keys, and ambient env; rejects with `ModelsError` codes oauth/auth — OAuth (Anthropic Claude Pro/Max, etc.) is wired via `lazyOAuth` in providers/anthropic.ts:15. — `packages/ai/src/auth/resolve.ts:40`
- `builtinProviders()` returns 34 provider factories (lines 72-107) spanning OpenRouter, Vercel/Groq/Cerebras/Together/Fireworks/Huggingface/Nvidia gateways, GitHub Copilot, Cloudflare, xAI, DeepSeek, MiniMax/Moonshot/Xiaomi/ZAI plus regional CN/AMS/SGP variants — far beyond the major-cloud set. — `packages/ai/src/providers/all.ts:70`
- `Model<TApi>` carries `api`, `provider`, `baseUrl`, `cost`, `contextWindow`, `maxTokens`, `input[]`, `thinkingLevelMap`, and a typed `compat` union (`OpenAICompletionsCompat`/`OpenAIResponsesCompat`/`AnthropicMessagesCompat`) with dozens of wire-compat flags (thinkingFormat with 10 enum values, cacheControlFormat, openRouterRouting, vercelGatewayRouting, sessionAffinityHeaders, supportsLongCacheRetention, supportsEagerToolInputStreaming, forceAdaptiveThinking, etc.). — `packages/ai/src/types.ts:683`
- `lazyApi(load)` wraps a dynamic `import()` of the api module so provider definitions are tree-shake safe and loaded on first stream call; each api module exports `stream`/`streamSimple` satisfying `ProviderStreams`. — `packages/ai/src/api/lazy.ts:63`
- A separate `ImagesApiProvider` registry (`registerImagesApiProvider`/`getImagesApiProvider`) dispatches image-GENERATION by `ImagesApi` string; built-in is openrouter-images (providers/all.ts:120) — an entire provider surface opi lacks. — `packages/ai/src/images-api-registry.ts:38`

## 2. Auth & credentials

**opi:** opi resolves credentials purely from process environment variables and TOML config at provider build time; there is no OAuth, no persistent credential store, no refresh, and no login/logout commands. AuthDescriptor is an introspection seam that reports presence/absence of env-var-backed keys (and a Bedrock credential-chain label) but never persists or rotates them.

Key facts:
- require_api_key reads the provider's API key from std::env::var(env_name) at construction; missing/empty env var is a fatal ProviderBuildError::Auth with no fallback to a stored credential. — `crates/opi-coding-agent/src/provider_factory.rs:102`
- build_runtime_provider resolves each built-in provider's key from env (require_api_key) or, for Bedrock (line 742-792), from config>env>AWS shared credential/config files + profile + credential_process via opi_ai::bedrock::credentials::resolve_credentials; there is no OAuth token path and no per-provider credential record. — `crates/opi-coding-agent/src/provider_factory.rs:631`
- resolved_auth_descriptor_for (the descriptor attached to a built provider at line 968) maps each built-in provider to an AuthDescriptor::Resolved{source} where source is 'env ANTHROPIC_API_KEY' etc. for env-key providers and 'aws credential chain' for Bedrock. auth_descriptor_for (line 875) instead returns AuthDescriptor::EnvApiKey{env_var} for all built-ins including Bedrock (env_var='AWS_ACCESS_KEY_ID'); no OAuth/refresh variant exists. — `crates/opi-coding-agent/src/provider_factory.rs:900`
- AuthDescriptor enum is #[non_exhaustive] with only StaticApiKey, EnvApiKey, Resolved variants; the doc comment (lines 90-96) states OAuth is 'an explicit future extension point and is not implemented'. — `crates/opi-ai/src/provider_collection.rs:97`
- opi doctor's provider_credential_probe reports credential presence only via env-var probe or (Bedrock) bedrock_credential_probe (config/env/profile checks); it never reads or writes a credential file and performs no network/auth validation. — `crates/opi-coding-agent/src/doctor.rs:602`

## 3. Provider catalog

**opi:** opi ships 9 built-in provider ids (anthropic, openai, openrouter, mistral, openai-responses, gemini, bedrock, azure, vertex) in a fixed array, plus user-declared openai_compatible config profiles. It has 7 dedicated wire-format Provider structs (Anthropic, OpenAiChat, OpenAiResponses, Gemini, Vertex, AzureOpenAI, Bedrock); openrouter and mistral are OpenAI-Chat profiles of OpenAiChatProvider, and the openai id itself is the canonical OpenAI-Chat instance. No provider carries an OAuth login flow; AuthDescriptor is API-key/resolved only with OAuth reserved as a future non_exhaustive variant.

Key facts:
- BUILT_IN_PROVIDER_IDS is a fixed array of 9: anthropic, openai, openrouter, mistral, openai-responses, gemini, bedrock, azure, vertex (registration order). — `crates/opi-coding-agent/src/provider_factory.rs:236`
- build_list_models_provider is a match over exactly those 9 ids; any other id returns 'unknown provider in built-in list'. — `crates/opi-coding-agent/src/provider_factory.rs:465`
- mistral_provider returns an OpenAiChatProvider (new_for_profile) -> Mistral is an OpenAI-Chat compatibility profile, not a dedicated wire implementation. — `crates/opi-ai/src/mistral.rs:18`
- openrouter_provider also returns an OpenAiChatProvider (new_for_profile) -> OpenRouter is an OpenAI-Chat compatibility profile. — `crates/opi-ai/src/openrouter.rs:19`
- compat_metadata_for marks openai, openrouter, AND mistral as openai_compatible=true; the other 6 built-in ids (anthropic, openai-responses, gemini, bedrock, azure, vertex) are not flagged. ## 18. Wire protocols & embedding

**opi:** opi defines three explicitly schema-versioned wire protocols (NDJSON v2, SDK/RPC v3, trace v1), each stamped on its first output header, plus a standalone streaming proxy and an opi-extension-jsonl-v1 adapter protocol. The embedding API is the opi-agent sdk module + opi-coding-agent CodingHarnessBuilder. There is no orchestrator/supervisor/radius equivalent, no typed subprocess RPC client, and no browser/web target.

Key facts:
- SDK_SCHEMA_VERSION: u32 = 3, marked unstable 0.x; SdkCommand enum has 12 variants (prompt/continue/steer/follow_up/abort/set_model/set_thinking_level/compact/session_info/extension_command/trace/quit) and is the shared command model for both RPC and embedding. — `crates/opi-agent/src/sdk.rs:42`
- NDJSON_SCHEMA_VERSION: u32 = 2 for --json mode; run_json emits a {type:"session_header", schema_version:2} line as the first stdout record (runner.rs:234-237) followed by a StartupDiagnostics event line. — `crates/opi-coding-agent/src/runner.rs:29`
- RPC mode emits an {type:"rpc_ready", schema_version:SDK_SCHEMA_VERSION, mode:"rpc", version:CARGO_PKG_VERSION, startup_diagnostics:[...]} header on stdout before processing commands; the same module stamps schema_version:TRACE_SCHEMA_VERSION on trace records (rpc.rs:938). — `crates/opi-coding-agent/src/rpc.rs:395-401`
- TRACE_SCHEMA_VERSION: u32 = 1 is a local, on-demand, opt-in trace envelope (not telemetry); TraceRecord carries schema_version + run_id + turn_id + sequence + TraceKind (non_exhaustive) and details are redacted via redact before leaving the process. — `crates/opi-agent/src/trace.rs:54`
- StreamingProxy emits a {type:"proxy_ready", schema_version:SDK_SCHEMA_VERSION} header (streaming_proxy.rs:178-183), reads JSONL commands, dispatches via ProxyHandler trait, applies bounded backpressure and an opt-in SecretRedactor (documented at streaming_proxy.rs:38-54) and a CancellationToken. — `crates/opi-agent/src/streaming_proxy.rs:178-183`
- Extension adapter protocol is versioned by string id PROTOCOL_VERSION = "opi-extension-jsonl-v1"; adapter_extension.rs:832 rejects adapters whose protocol field differs (returns a diagnostic_for_unsupported_adapter_protocol and continues). — `crates/opi-coding-agent/src/adapter_protocol.rs:86`
- Public embedding surface re-exports SDK_SCHEMA_VERSION, SdkCommand, SdkResponse (lib.rs:40), the streaming proxy types (lib.rs:43-45), and the trace collector/sinks (lib.rs:47-50); opi-coding-agent exposes CodingHarness + CodingHarnessBuilder (harness.rs:107, 318). — `crates/opi-agent/src/lib.rs:40-50`
