## 1. Provider 抽象与分发

**opi：** opi 将 provider 建模为一个仅支持流式的 `Provider` trait（`id`/`models`/`stream`），由 8 个具体 provider 类型实现，外加一个 MockProvider 和一个不可分发的 MetadataProvider，通过两层 `ProviderRegistry`（解析 `provider:model` 规范）分发，再由 `ProviderCollection` 包裹以添加 auth 门控分发和 OpenAI 兼容元数据。集中式的 `provider_factory.rs` 根据 TOML 配置 + 环境变量构建活动 provider 以及所有已注册模型；agent 循环在一个注入的 `Box<dyn Provider>` 上直接调用 `provider.stream(request)`（模型 id 可在运行中通过 `Agent::set_model` 改变，但 provider 对象是固定的）。没有动态/异步模型发现，没有 OAuth 登录，没有 `complete` trait 方法（complete 分发会耗尽 stream），没有 `streamSimple` 变体，也没有图像生成面。

关键事实：

- `Provider` trait 有三个方法：`id()`、`models() -> &[ModelInfo]`、`stream(request: Request) -> EventStream`；trait 上没有 `complete`/`refresh`/auth 方法。 — `crates/opi-ai/src/provider.rs:12`
- `Request` 是一个扁平 struct（model、system、messages、tools、max_tokens、temperature、thinking、stop_sequences、metadata、cancel: CancellationToken）；auth/baseUrl/headers 不在 request 中 —— 它们在构造时被烤入具体 provider。 — `crates/opi-ai/src/provider.rs:30`
- `ProviderRegistry` 通过 `split_spec`（单个冒号，拒绝空半段）解析 `provider:model` 字符串，支持运行时 `register_provider`/`register_model` 覆盖，并在 `all_models()` 中为 `--list-models` 去重覆盖项；没有 async，没有 fetch。 — `crates/opi-ai/src/registry.rs:117`
- `ProviderCollection` 包裹一个 `ProviderRegistry` 并添加 `AuthDescriptor`（StaticApiKey/EnvApiKey/Resolved）、`CompatMetadata`，以及 `dispatch_stream`/`dispatch_complete`；complete 分发（位于 :359 的 `dispatch_complete`）会耗尽流式 trait（`Provider` 上没有单独的 complete 方法）。 — `crates/opi-ai/src/provider_collection.rs:245`
- `refresh()` 是一个有文档说明的 no-op 桩（`Ok(())`）：没有实现任何 refresh 行为；opi-ai 中没有任何动态模型目录 fetch。 — `crates/opi-ai/src/provider_collection.rs:374`
- 9 个内置 provider id 被硬编码（`BUILT_IN_PROVIDER_IDS`：anthropic、openai、openrouter、mistral、openai-responses、gemini、bedrock、azure、vertex）；`build_runtime_provider` 通过 match 分发到各 provider 的构造器，这些构造器读取环境变量/配置并返回 `Box<dyn Provider>`。 — `crates/opi-coding-agent/src/provider_factory.rs:236`
- `build_provider` 从 `config.defaults.model`（单个 `provider:model` 规范）中选择一个活动 provider；agent 循环接收该单个 provider 对象 —— 循环层没有按请求进行的多 provider 路由（只有通过 `Agent::set_model` 在同一 provider 内切换 model-id）。 — `crates/opi-coding-agent/src/provider_factory.rs:620`
- 自定义 provider 仅支持 OpenAI-Chat 兼容配置（`OpenAiCompatibleProviderConfig` -> `OpenAiChatProvider::new_for_profile`）；若不编写 Rust，则无法通过配置注册非 OpenAI 的自定义 provider。 — `crates/opi-coding-agent/src/config.rs:177`
- `CompatConfig` 恰好携带 9 个标志（system_role_override、max_tokens_field、tool_result_name_field、usage_in_stream、strict_tool_schema、reasoning_effort、cache_key、require_assistant_after_tool_result、chat_completions_path）；`extra_headers` 位于 profile/provider 上，而非 CompatConfig。 — `crates/opi-ai/src/openai_chat.rs:708`
- 分发到 wire 上的调用是 `AgentLoopContext.provider: Box<dyn Provider>` 上的 `context.provider.stream(request)`；在活动运行路径上，collection/auth 接缝被绕过（harness 仅使用 MetadataProvider 用于列表展示）。 — `crates/opi-agent/src/agent_loop.rs:118`
- opi-ai 中存在 8 个具体的 `impl Provider for` 类型：AnthropicProvider、OpenAiChatProvider、OpenAiResponsesProvider、GeminiProvider、AzureOpenAIProvider、BedrockProvider、VertexProvider（外加 test_support 中的 MockProvider 和 provider_factory 中的 MetadataProvider）。anthropic.rs 中不存在任何 anthropic-cache_control/eager_input/adaptive/session-affinity 处理。 — `crates/opi-ai/src/anthropic.rs:1004`

**pi：** pi 将 provider 建模为一个数据型 `Provider` 对象（`id`/`name`/`auth`/`getModels`/`stream`/`streamSimple`/可选的 `refreshModels`），由一个 `createProvider` 工厂构建，其 `api` 字段是一个以 `model.api` 字符串为键的 map，分发到懒加载的 API 实现模块。`Models` collection 按请求解析 auth（api-key + OAuth，带双重检查的刷新锁），暴露四个分发原语（stream、complete、streamSimple、completeSimple），并且有 34 个内置 provider 工厂位于 `providers/all.ts`；还有一个独立的图像生成 registry（`ImagesModels`）。

关键事实：

- `Provider<TApi>` 接口：`id`、`name`、`baseUrl?`、`headers?`、`auth: ProviderAuth`（必填）、`getModels()`、可选的 async `refreshModels()`，外加 `stream` 与 `streamSimple`；auth 是一等公民的按 provider 属性，而非独立的接缝。 — `packages/ai/src/models.ts:33`
- `createProvider` 通过 `api` 字段在 `model.api` 上分发，该字段要么是单个 `ProviderStreams`，要么是 `Partial<Record<TApi, ProviderStreams>>`；某个 model 的 api 没有对应条目时会产生 `ModelsError('stream')` —— provider 是 api 多路复用的，而非每个后端单体化。 — `packages/ai/src/models.ts:324`
- `ModelsImpl.stream` 在异步 auth 解析（`applyAuth` 然后 `provider.stream`）之上包了一层 `lazyStream`；auth 是按请求解析的，而非在构造时烤入，并且会将 request options 与已解析的 auth 合并。 — `packages/ai/src/models.ts:259`
- `ModelsImpl.refresh(provider?)` 调用每个 provider 可选的 `refreshModels()`（models.ts:214 处跨 provider 并发 allSettled；models.ts:354-364 处按 provider 扇出）；没有 `refreshModels` 的静态 provider 为 no-op —— 动态模型发现是一等公民能力。 — `packages/ai/src/models.ts:199`
- `resolveProviderAuth` 处理已存储的 OAuth 凭据（在 `CredentialStore.modify` 下带双重检查的刷新锁，位于 auth/resolve.ts:86 的 resolveStoredOAuth）、已存储的 api key 以及环境 env；以 `ModelsError` 代码 oauth/auth 拒绝 —— OAuth（Anthropic Claude Pro/Max 等）通过 providers/anthropic.ts:15 的 `lazyOAuth` 接入。 — `packages/ai/src/auth/resolve.ts:40`
- `builtinProviders()` 返回 34 个 provider 工厂（第 72-107 行），涵盖 OpenRouter、Vercel/Groq/Cerebras/Together/Fireworks/Huggingface/Nvidia 网关、GitHub Copilot、Cloudflare、xAI、DeepSeek、MiniMax/Moonshot/Xiaomi/ZAI 以及区域性的 CN/AMS/SGP 变体 —— 远超主流云厂商集合。 — `packages/ai/src/providers/all.ts:70`
- `Model<TApi>` 携带 `api`、`provider`、`baseUrl`、`cost`、`contextWindow`、`maxTokens`、`input[]`、`thinkingLevelMap`，以及一个类型化的 `compat` 联合体（`OpenAICompletionsCompat`/`OpenAIResponsesCompat`/`AnthropicMessagesCompat`），带数十个 wire 兼容标志（thinkingFormat 有 10 个枚举值、cacheControlFormat、openRouterRouting、vercelGatewayRouting、sessionAffinityHeaders、supportsLongCacheRetention、supportsEagerToolInputStreaming、forceAdaptiveThinking 等）。 — `packages/ai/src/types.ts:683`
- `lazyApi(load)` 包裹了对 api 模块的动态 `import()`，使 provider 定义可 tree-shake 安全并在首次 stream 调用时加载；每个 api 模块导出满足 `ProviderStreams` 的 `stream`/`streamSimple`。 — `packages/ai/src/api/lazy.ts:63`
- 一个独立的 `ImagesApiProvider` registry（`registerImagesApiProvider`/`getImagesApiProvider`）按 `ImagesApi` 字符串分发图像生成；内置为 openrouter-images（providers/all.ts:120）—— 一整套 opi 所缺失的 provider 面。 — `packages/ai/src/images-api-registry.ts:38`

## 2. 认证与凭据

**opi:** opi 在 provider 构建时仅从进程环境变量和 TOML 配置解析凭据；没有 OAuth，没有持久化凭据存储，没有刷新，也没有 login/logout 命令。AuthDescriptor 是一个内省接缝，用于报告基于环境变量的密钥存在/缺失情况（以及 Bedrock 凭据链标签），但从不持久化或轮换它们。

关键事实：

- require_api_key 在构造时通过 std::env::var(env_name) 读取 provider 的 API key；缺失/空环境变量是致命的 ProviderBuildError::Auth，没有回退到已存储凭据。— `crates/opi-coding-agent/src/provider_factory.rs:102`
- build_runtime_provider 从环境变量（require_api_key）或对于 Bedrock（第 742-792 行）从 config>env>AWS 共享凭据/配置文件 + profile + credential_process（通过 opi_ai::bedrock::credentials::resolve_credentials）解析每个内置 provider 的密钥；没有 OAuth token 路径，也没有 per-provider 凭据记录。— `crates/opi-coding-agent/src/provider_factory.rs:631`
- resolved_auth_descriptor_for（在第 968 行附加到已构建 provider 的描述符）将每个内置 provider 映射到 AuthDescriptor::Resolved{source}，其中 source 对于环境变量密钥 provider 是 'env ANTHROPIC_API_KEY' 等，对于 Bedrock 是 'aws credential chain'。auth_descriptor_for（第 875 行）则对所有内置 provider（包括 Bedrock）返回 AuthDescriptor::EnvApiKey{env_var}（env_var='AWS_ACCESS_KEY_ID'）；不存在 OAuth/refresh 变体。— `crates/opi-coding-agent/src/provider_factory.rs:900`
- AuthDescriptor 枚举是 #[non_exhaustive] 的，仅有 StaticApiKey、EnvApiKey、Resolved 变体；文档注释（第 90-96 行）声明 OAuth 是“一个明确的未来扩展点，目前未实现”。— `crates/opi-ai/src/provider_collection.rs:97`
- opi doctor 的 provider_credential_probe 仅通过环境变量探针或（Bedrock 的）bedrock_credential_probe（config/env/profile 检查）报告凭据存在情况；它从不读写凭据文件，也不执行任何网络/认证验证。— `crates/opi-coding-agent/src/doctor.rs:602`
- VertexProvider::new 使用一个已解析的 access_token String 构造；opi 不读取 gcloud application_default_credentials.json，也不执行 ADC 解析（crates/ 中任何位置都不存在 GOOGLE_APPLICATION_CREDENTIALS / application_default_credentials 引用）。— `crates/opi-ai/src/vertex.rs:48`
- opi Bedrock 凭据解析优先级是 显式 config > 环境变量 > 共享 AWS 凭据/配置 profile 文件 > credential_process；模块注释（第 142-144 行）明确声明“无 IMDS、SSO 浏览器/设备流程或 web-identity 网络调用”。AWS_BEARER_TOKEN_BEDROCK、ECS task-role URI（AWS_CONTAINER_CREDENTIALS_*）和 IRSA web-identity（AWS_WEB_IDENTITY_TOKEN_FILE）不受支持。— `crates/opi-ai/src/bedrock/credentials.rs:89`
- 任何 opi crate 中都不存在 OAuth provider、refresh-token 轮换、持久化 auth.json 存储、/login 或 /logout 命令、--api-key 标志或交互式凭据设置流程；唯一的 refresh_token 出现位置是 opi-ai/src/http.rs:278 中的一个 URL 脱敏正则。— absent: searched crates/opi-coding-agent/src/cli.rs (no login/logout/--api-key flags), config.rs (only api_key_env/access_token_env name config), and grepped 'oauth|refresh_token|/login|/logout|auth.json|keytar|keychain|credential_store' across crates/

**pi:** pi 拥有完整的凭据系统：一个持久化的 auth.json 存储（每个 provider 一个带类型标签的凭据，通过 proper-lockfile 文件锁定，模式 0600），针对 Anthropic（Claude Pro/Max）、GitHub Copilot 和 OpenAI Codex（ChatGPT）的 OAuth provider（支持 login/refresh/logout），ambient env/ADC/AWS 链回退，以及可检查的认证状态（不暴露密钥也不发起请求）。

关键事实：

- AuthStorage 类将 per-provider 凭据映射持久化到 getAgentDir()/auth.json（通过 FileAuthStorageBackend）；文件以模式 0o600 写入（AUTH_FILE_WRITE_OPTIONS 第 53 行），父目录模式 0o700（第 70 行），所有写入都通过 proper-lockfile（import 第 19 行）经 withLock/withLockAsync 锁定。— `packages/coding-agent/src/core/auth-storage.ts:203`
- getApiKey（声明于第 473 行）优先级是：1) 运行时 --api-key 覆盖（runtimeOverrides），2) 来自 auth.json 的已存储 api_key，3) 在 Date.now() >= expires 时于锁下自动刷新的已存储 OAuth token（refreshOAuthTokenWithLock），若刷新失败则重新读取文件以复用另一实例的成功结果，4) 通过 getEnvApiKey 获取 ambient 环境变量。— `packages/coding-agent/src/core/auth-storage.ts:466`

## 6. 会话模型

**opi:** opi 使用仅追加的 JSONL 格式版本 1，带有一个 `#[non_exhaustive]` 的 `SessionEntry` 枚举（9 个变体：`message`、`compaction`、`leaf`、`extension_state`、`session_info`、`model_change`、`thinking_level_change`、`label`、`branch_summary`）。存储是构建于文件之上的轻量 `SessionWriter`/`SessionReader`，加上一个 `SessionRepo` trait（`append`/`load`/`message_count`），其实现为 `JsonlSessionRepo`；只读的树重建（`SessionTree`）位于 opi-agent，而 fork/list/delete 是 opi-coding-agent 中的产品层函数。压缩是一个确定性的核心引擎，带有 `CompactionHooks` trait 缝合点；它从不调用 LLM，并回退到基于字符数的截断。前向兼容通过未知类型跳过（`CrashRecovery.unknown_count`）实现，而非格式迁移；`header.version != 1` 被硬拒绝。

关键事实：

- `FORMAT_VERSION = 1`；`SessionHeader` 携带 type/version/id/timestamp/cwd/parent_session。`SESSION_FORMAT_POLICY`（session.rs:58-61）明确声明不兼容 pi-session-v3。— `crates/opi-agent/src/session.rs:53`
- `SessionEntry` 枚举是 `#[non_exhaustive]` 的，有 9 个变体（`Message`、`Compaction`、`Leaf`、`ExtensionState`、`SessionInfo`、`ModelChange`、`ThinkingLevelChange`、`Label`、`BranchSummary`）。元数据变体挂接到内容末端，但既不推进末端也不进入分支图（session.rs:226-242）。— `crates/opi-agent/src/session.rs:194-208`
- `CrashRecovery` 是一个带有三个独立字段（`truncated_line`、`corrupt_count`、`unknown_count`）的结构体。未知类型条目（合法 JSON 但 `type` 无法识别）被跳过并计数，从不致命；`KNOWN_ENTRY_TYPES` 固定于 session.rs:515-525。— `crates/opi-agent/src/session.rs:259-264,480-496`
- Reader 硬拒绝 `header.version != FORMAT_VERSION`，错误为 'unsupported session version'；没有迁移命令或跨版本加载器。新的条目变体在 v1 内是累加的（session.rs:9-14）。— `crates/opi-agent/src/session.rs:449-457`
- `SessionTree::from_entries` 根据 `parent_id` 图 + `Leaf` 指针构建分支（仅为图索引 `Message`/`Compaction`，行 65-95）；`active_tip` 解析到上一个有效的 `Leaf` 目标，否则回退到主干末端（session_branch.rs:173-182）。— `crates/opi-agent/src/session_branch.rs:56-161`
- `reconstruct_context` 遍历活动链 root->tip，应用压缩（丢弃严格位于 `first_kept_entry_id` 之前的消息，在 session_context.rs:355-371 注入 `CompactionSummary`），在其父节点之后注入 `BranchSummary`（行 209-221），并收集挂接到活动链的元数据（后写覆盖的 model/thinking/name、Add/Remove labels、extension_state）（collect_metadata，行 388-429）。— `crates/opi-agent/src/session_context.rs:120-242`
- `CompactionEngine::compact` 是确定性的：`find_split_point` 保留最后 25%（min 1）的条目（compaction.rs:185-201）；`hooks.generate_summary` 返回 `Option<String>`，否则 `generate_core_summary` 截断到约 500 字符（compaction.rs:263-280）。token 估算为 chars/4（`estimate_message_tokens`，行 214-217）。opi-agent 中不存在任何 LLM/provider 调用。— `crates/opi-agent/src/compaction.rs:124-181`
- `SessionRepo` trait 只有 append/load/message_count。list/fork/delete 与目录策略被排除；由 opi-coding-agent 拥有（session_cli.rs:131 `list_sessions`，:210 `fork_session`，:298 `delete_session`）。唯一的内存中 `SessionRepo` 实现仅用于测试（tests/session_facade.rs:235 中的 `RecordingSessionRepo`）。— `crates/opi-agent/src/harness.rs:625-634`
- `fork_session` 过滤条目到活动链，并在活动内容末端写入单个全新的 `Leaf`；它不接受 entryId/position 参数，无法在任意用户消息处或之前 fork。— `crates/opi-coding-agent/src/session_cli.rs:210-258`

**pi:** pi 使用仅追加的 JSONL 格式版本 3，有 11 个 `SessionTreeEntry` 类型（`message`、`thinking_level_change`、`model_change`、`active_tools_change`、`compaction`、`branch_summary`、`custom`、`custom_message`、`label`、`session_info`、`leaf`）。存储是分层库级抽象：一个 `SessionStorage` 接口（12 个方法，包括 `getPathToRoot`/`findEntries`/`getLabel`），实现有 `JsonlSessionStorage` + `InMemorySessionStorage`，外层由一个 `SessionRepo` 接口（`create`/`open`/`list`/`delete`/`fork`）包装，其实现为 `JsonlSessionRepo`。压缩与分支摘要是 LLM 驱动的，通过 `models.completeSimple` 配合结构化 prompt，并跟踪读/修改的文件操作。启动时 migrations.ts 会迁移遗留会话文件。

## 7. Extension/插件面

**opi:** opi 的 extension 面分为两层：(1) opi-agent 中的 Rust `Extension` trait + `ExtensionRegistry`，提供生命周期 hook、自定义工具、自定义命令、自定义 provider（通过 `Box<dyn Provider>`）、模型覆盖、事件观察以及按 extension 的状态序列化；(2) opi-coding-agent 中的进程外 JSONL adapter 协议（`opi-extension-jsonl-v1`），通过 `ProcessAdapter` 将外部子进程桥接到同一个 `Extension` trait。注册在启动时即被锁定（一旦 extension 列表被 wrap_hooks/wrap_event_sink 以 Arc 共享，registry 会拒绝变更）。没有进程内 extension UI 上下文，没有自定义消息/条目渲染器，没有 TUI 组件/footer/header/widget/autocomplete/editor 工厂，没有键盘快捷键或 CLI flag 注册，没有跨 extension 的共享事件总线（仅在 Agent 上有一个 host 级的 AgentEvent 订阅者，对 extension 而言只读），也没有子 Agent/编排器；子 Agent 仅作为示例 package/测试存在，明确声明不属于核心。opi 的 AgentHooks 没有 provider 请求/payload/response hook。

## 18. Wire 协议与嵌入

**opi:** opi 定义了三种显式带 schema 版本的 wire 协议（NDJSON v2、SDK/RPC v3、trace v1），每种都在其首个输出头部上盖章，外加一个独立的 streaming proxy 和一个 opi-extension-jsonl-v1 adapter 协议。嵌入 API 是 opi-agent 的 sdk 模块 + opi-coding-agent 的 CodingHarnessBuilder。不存在 orchestrator/supervisor/radius 等价物，没有类型化子进程 RPC 客户端，也没有 browser/web 目标。

关键事实：

- SDK_SCHEMA_VERSION: u32 = 3，标记为 unstable 0.x；SdkCommand 枚举有 12 个变体（prompt/continue/steer/follow_up/abort/set_model/set_thinking_level/compact/session_info/extension_command/trace/quit），是 RPC 和嵌入共享的命令模型。 — `crates/opi-agent/src/sdk.rs:42`
- NDJSON_SCHEMA_VERSION: u32 = 2 用于 --json 模式；run_json 发出一条 {type:"session_header", schema_version:2} 行作为首条 stdout 记录（runner.rs:234-237），其后跟一条 StartupDiagnostics 事件行。 — `crates/opi-coding-agent/src/runner.rs:29`
- RPC 模式在处理命令之前，于 stdout 上发出 {type:"rpc_ready", schema_version:SDK_SCHEMA_VERSION, mode:"rpc", version:CARGO_PKG_VERSION, startup_diagnostics:[...]} 头部；同一模块在 trace 记录上盖章 schema_version:TRACE_SCHEMA_VERSION（rpc.rs:938）。 — `crates/opi-coding-agent/src/rpc.rs:395-401`
- TRACE_SCHEMA_VERSION: u32 = 1 是一个本地、按需、opt-in 的 trace envelope（不是 telemetry）；TraceRecord 携带 schema_version + run_id + turn_id + sequence + TraceKind（non_exhaustive），详细信息在离开进程前通过 redact 进行脱敏。 — `crates/opi-agent/src/trace.rs:54`
- StreamingProxy 发出 {type:"proxy_ready", schema_version:SDK_SCHEMA_VERSION} 头部（streaming_proxy.rs:178-183），读取 JSONL 命令，通过 ProxyHandler trait 分发，应用有界反压和一个 opt-in 的 SecretRedactor（记录于 streaming_proxy.rs:38-54）以及一个 CancellationToken。 — `crates/opi-agent/src/streaming_proxy.rs:178-183`
- Extension adapter 协议由字符串 id PROTOCOL_VERSION = "opi-extension-jsonl-v1" 进行版本化；adapter_extension.rs:832 拒绝 protocol 字段不同的 adapter（返回一个 diagnostic_for_unsupported_adapter_protocol 并继续）。 — `crates/opi-coding-agent/src/adapter_protocol.rs:86`
- 公共嵌入面重新导出 SDK_SCHEMA_VERSION、SdkCommand、SdkResponse（lib.rs:40），streaming proxy 类型（lib.rs:43-45），以及 trace collector/sink（lib.rs:47-50）；opi-coding-agent 暴露 CodingHarness + CodingHarnessBuilder（harness.rs:107, 318）。 — `crates/opi-agent/src/lib.rs:40-50`
- opi 没有 wasm32/browser/web 目标，没有 orchestrator/supervisor/radius/IPC-socket-serve 等价物，也没有内置的子进程 RPC 客户端。 — absent: searched crates/opi-*/src/*.rs for wasm32|browser|web-sys|wasm-bindgen (0 hits in src), for orchestrator|supervisor|radius (only a doc-guard test helper param), and for struct RpcClient / spawn --mode rpc (0 hits)
