## 1. Provider abstraction and dispatch

**opi:** opi defines an object-safe `Provider` trait (id/models/stream/replace_model_catalog/refresh_models) in `opi-ai`, a `ProviderRegistry` that resolves `provider:model` spec strings with a 3-layer catalog (overrides > dynamic > built-in), and a `ProviderCollection` facade that adds auth-gated dispatch. Multi-wire providers are assembled as `ApiMappedProvider` (one route per `WireApi`) with full route-graph validation at construction. The binary centralizes all concrete provider construction in `provider_factory.rs`.

## 2. Authentication and credentials

**opi:** opi defines an object-safe CredentialStore (read/write/delete/probe) and a per-request AuthResolver in opi-ai, with the concrete OS-keychain backend (keyring-core), versioned JSON envelope, cross-process fs4 lock, keychain-first/env-fallback API-key resolver, and three OAuth providers (Anthropic PKCE, OpenAI Codex browser+device-code, GitHub Copilot device-code) in opi-coding-agent. All secret fields are secrecy::SecretString (zeroize on drop) with manual redacting Debug; providers call auth.resolve() inside each stream. Doctor/--list-models inspect presence via a secret-free marker probe.

## 7. Extension and plugin surface

**opi:** opi exposes a single in-process Rust `Extension` trait (static, Send+Sync) plus an `AgentHooks` base trait; the only dynamic/out-of-process surface is a versioned JSONL adapter protocol (`opi-extension-jsonl-v1`) that bridges a child process into the same Extension trait. ## 14. Permissions and sandbox
