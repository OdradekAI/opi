# pi 0.84.1 package 架构动作与 Opi 对齐判断

> 日期：2026-08-13  
> 性质：非规范性 inward alignment evidence；不修改 `docs/opi-spec.md` 的权威。  
> 范围：仅审阅固定本地快照 `.repo/pi-0.84.1` 与当前 Opi 一手材料；未联网。  
> 结论标签：**必须调整**表示当前 Opi 已有语义或文档需要收口；**观察**表示保留为后续 Placement Review 输入；**不要跟随**表示当前没有足够消费者或会违反 Opi 的既定边界。

## 结论先行

pi 0.84.1 的“大动作”不是简单增加几个 npm 包，而是在原有 CLI/Agent runtime 外围搭建一套尚未纵向闭合的 **durable session platform**：

```text
                         @pi-telemetry
                           ↑       ↑
                        @pi-ai → @pi-agent-core
                           ↑          ↑
                           │          └── session backends / AgentHarness v2
                           │
@pi-protocol ← @pi-client  │  @pi-server
       ↑           ↑       │      ↑
       └──────── @pi-coding-agent ┘      (service assembly 尚缺)

@pi-evals (private) → real coding-agent AgentSession
```

它同时做了四件事：

1. 把 session 从“对话 JSONL”提升为 tree + lanes + operation logs + global facts 的 durable state；
2. 把远程会话拆成 runtime-neutral protocol、client 与 server core；
3. 把 telemetry 抽成显式上下文、无 exporter 的独立契约包；
4. 增加直接运行真实 `AgentSession` 的内部 eval harness。

但这些部件并不等于“远程 durable coding agent 已完成”：v4 session/storage 是真实实现，protocol/client/server transport core 也有真实代码与测试；核心 `AgentHarness` 的 prompt、resume、abort、watch、lane 等 operation surface 仍统一返回 `HarnessNotImplemented`，server 没有 coding-agent service/CLI，SQLite backend 也没有产品消费者。pi 自己把 server 与 protocol 标为 experimental，并明确把 coding-agent 迁移排除在 `harness-v2` 当前范围外。来源：[`packages/agent/CHANGELOG.md`](../../.repo/pi-0.84.1/packages/agent/CHANGELOG.md):17-28、[`agent-harness.ts`](../../.repo/pi-0.84.1/packages/agent/src/harness/agent-harness.ts):347-420、[`server/README.md`](../../.repo/pi-0.84.1/packages/server/README.md):1-5,36-40、[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):35-41。

对 Opi 的总判断：**不需要因为 pi 新增 package 而改变当前六 crate 拓扑，也不应撤销 Phase 17 删除未接入 `AgentHarness` 状态所有者的决定。** Opi 规范已经准确预判了这批信号：remote-session adapter 属于 Extension Ecosystem，实验性 pi protocol/client/server 与 broad harness 在出现真实 Opi 消费者前只作观察；新 pi package 本身不建立优先级。来源：[`docs/opi-spec.md`](../opi-spec.md):119-131,157-172,594-599。

当前需要做的不是追包，而是收紧三处已有方向：

- 完成 Phase 17 已开始的 provider dispatch、完整 next-turn state、可信 tool authority 与 evidence activation；当前 evidence 模块自己声明仍只是 additive substrate，尚未接入 `agent_loop`。来源：[`evidence.rs`](../../crates/opi-agent/src/evidence.rs):1-10、[`docs/opi-spec.md`](../opi-spec.md):571-577。
- 清理仍把已删除 `AgentHarness` 描述为未来产品迁移目标的陈旧模块注释；当前 README 已明确它在 Phase 17.2 被删除，但 `opi-agent::harness` 与 `CodingHarness` 注释还在描述旧关系。来源：[`opi-agent/README.md`](../../crates/opi-agent/README.md):345-371、[`opi-agent/src/harness.rs`](../../crates/opi-agent/src/harness.rs):3-31、[`opi-coding-agent/src/harness.rs`](../../crates/opi-coding-agent/src/harness.rs):414-423。
- 将 `Agent` 对 `NextTurnState` 的 “durable owner” 表述限定为 **进程内 live state 的唯一所有者**；若未来引入真正 durable harness，跨进程事实源应是 operation/session log，经 reduction 重建并原子替换 live state。来源：[`loop_types.rs`](../../crates/opi-agent/src/loop_types.rs):112-138、[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):650-675。

除此之外，remote protocol/client/server、lane runtime、SQLite backend 与 telemetry 独立 crate 都应继续观察，不进入当前 Opi 实现计划。

## 3. pi 的四个主要架构动作

### 3.1 从 transcript persistence 转向 durable orchestration log

`harness-v2` 把 session 定义为四部分：

1. append-only conversation tree；
2. named lane pointers；
3. per-lane operation logs；
4. global latest-value facts。

所有写入共享单调 `seq`。每个 lane 同时最多一个 operation，不同 lanes 可并行；prompt、queue/deferred write 在 API resolve 前先 durable acceptance。外部 effect 前写 intent，effect 后用预分配 ID 写 result。来源：[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):43-77,100-127,174-180。

这个变化的关键不在“SQLite”或“lane”本身，而在事实源：live lane state 是 records + entries 的 reduction。正常运行在每次 durable write 后更新内存，恢复时从 storage 重算；二者不再是独立真相。来源：[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):650-675。

v4 storage contract 已是这条路线最扎实的部分：Memory、JSONL、SQLite 共享 conformance；SQLite 增加 bounded query、durable operation records、shared sequence、statistics 与 fenced writer leases。测试矩阵明确说 storage/query 大量已覆盖，同时也明确 runtime stream behavior 仍主要未覆盖，因为 `AgentHarness` 仍是 scaffold。来源：[`agent/CHANGELOG.md`](../../.repo/pi-0.84.1/packages/agent/CHANGELOG.md):17-28、[`sqlite-node/CHANGELOG.md`](../../.repo/pi-0.84.1/packages/session-backends/sqlite-node/CHANGELOG.md):13-26、[`harness-v2-test-matrix.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2-test-matrix.md):18-33。

### 3.2 从进程内 CLI/RPC 扩展到 remote session control plane

`pi-protocol` 定义严格的 version-1 binary wire：`uint32-be length + CBOR payload`，hello/version negotiation、request/response correlation、server event envelope，并规定 session/server snapshots 才是 authoritative，progress 不能乐观归并成状态。来源：[`protocol/README.md`](../../.repo/pi-0.84.1/packages/protocol/README.md):3-16,40-50。

`pi-client` 在 wire 上增加连接与 session ownership：一个 connection 可 attach 多个 sessions，snapshot/response authoritative；exclusive/shared lease 决定本地协调权，detach/dispose failure 有显式恢复语义。来源：[`client/README.md`](../../.repo/pi-0.84.1/packages/client/README.md):26-40。

`pi-server` 则把 transport、protocol state 与 Agent implementation 分开：它只依赖 ai + protocol，通过应用提供的 `PiServerService` 获取 durable metadata 与 acquired runtime。它不提供 standalone CLI 或 coding-agent service，认证/授权也由 listener 在交付 connection 前完成。来源：[`server/package.json`](../../.repo/pi-0.84.1/packages/server/package.json):49-51、[`server/README.md`](../../.repo/pi-0.84.1/packages/server/README.md):7-40。

这个 ownership 分层是有价值的，但当前没有闭合为产品：

- coding-agent 发布 `./client` subpath，却没有 `./server` export；来源：[`coding-agent/package.json`](../../.repo/pi-0.84.1/packages/coding-agent/package.json):14-23。
- server 不依赖 agent-core 或 SQLite backend；应用 service 是空位；来源：[`server/package.json`](../../.repo/pi-0.84.1/packages/server/package.json):49-51。
- coding-agent 主运行类仍直接持有 `Agent` 与 `SessionManager`；来源：[`agent-session.ts`](../../.repo/pi-0.84.1/packages/coding-agent/src/core/agent-session.ts):302-308。
- coding-agent 虽有 `src/server/create-harness.ts` 组装 helper，但它未进入 package exports，而被组装的 `AgentHarness` 又不能执行 prompt。来源：[`create-harness.ts`](../../.repo/pi-0.84.1/packages/coding-agent/src/server/create-harness.ts):78-151、[`agent-harness.ts`](../../.repo/pi-0.84.1/packages/agent/src/harness/agent-harness.ts):347-420。

因此它是“已有真实横向部件、尚无真实纵向产品”的 platform construction。

### 3.3 把 observability 变成显式、可适配但非持久状态的契约

`pi-telemetry` 的设计很克制：显式 callback context、noop 与 deterministic in-memory reference、无 exporter、无 global current span、无 `AsyncLocalStorage` 依赖，并提供 adapter conformance。domain schema 由 agent-core 拥有，adapter 可翻译到 OTel/Sentry/log。来源：[`telemetry/README.md`](../../.repo/pi-0.84.1/packages/telemetry/README.md):1-13,118-132、[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):2751-2763。

但必须区分“契约完成”与“产品 coverage 完成”：pi-ai 按设计只接受 `TelemetryContext`，自己不拥有 span schema，也不发 telemetry；agent-owned request/harness spans 依赖 harness execution，而当前 operation runtime 仍未实现。来源：[`harness-v2.md`](../../.repo/pi-0.84.1/packages/agent/docs/harness-v2.md):2757-2763、[`agent-harness.ts`](../../.repo/pi-0.84.1/packages/agent/src/harness/agent-harness.ts):355-420。

### 3.4 引入真实 AgentSession eval，但仍是项目内行为回归工具

`pi-evals` 不是空目录：它在隔离的临时 project/agent 目录运行真实 `AgentSession`，保存 native session JSONL，支持 baseline/candidate、重复试验、judge score、tokens/latency/cost 分离和 missing telemetry。来源：[`evals/README.md`](../../.repo/pi-0.84.1/packages/evals/README.md):1-5,32-40,104-150。

但它也不是 Opi 规范中的 Independent cross-Agent Eval：package 是 private，直接 dev-depend `pi-coding-agent`，使用 pi-native session artifacts 与 `vitest-evals`，没有 Agent/Grader process adapters、ATIF、native benchmark grader provenance、content-addressed run bundle 或 offline recomputation contract。来源：[`evals/package.json`](../../.repo/pi-0.84.1/packages/evals/package.json):1-18；对比 [`docs/opi-spec.md`](../opi-spec.md):249-289。

## 4. 与当前 Opi 架构的逐层比较

### 4.1 Workspace placement

Opi 当前六 crate 拓扑是：

```text
opi-ai                    opi-tui
  ↑                         ↑
opi-agent                  │
  ↑                         │
opi-coding-agent ───────────┘

opi-protocol ← opi-sandbox
```

`opi-ai`/`opi-agent` 是 Agent Core；`opi-tui`/`opi-coding-agent` 是 Reference Product；`opi-protocol`/`opi-sandbox` 是 agent-neutral command-execution companion path。来源：[`Cargo.toml`](../../Cargo.toml):1-25、[`docs/opi-spec.md`](../opi-spec.md):157-164。

这和 pi 0.84.1 的 package 名称不能一一对应：Opi 的 `opi-protocol` 是 `command-execution-jsonl-v1`，明确只服务 host ↔ execution backend，不是 remote Agent session protocol。未来若实验 remote session wire，必须使用独立 wire identity 与 placement，不能把 pi-protocol 的 schema 塞进现有 `opi-protocol` 并模糊两个 authority boundary。来源：[`opi-protocol/README.md`](../../crates/opi-protocol/README.md):1-31,44-63。

### 4.2 Runtime ownership

Opi 当前产品路径直接组合 `CodingHarness → Agent + ProviderCollection + SessionCoordinator`；`CodingHarness` 持有 `Agent` 与可选 `SessionCoordinator`，没有第二个 runtime harness 状态所有者。来源：[`opi-coding-agent/src/harness.rs`](../../crates/opi-coding-agent/src/harness.rs):414-450。

Phase 17 的 `NextTurnState` 把完整 conversation context、canonical provider/model selection 和 inference config 作为一次完整替换；这与 pi durable harness 的 live-state reduction 可以兼容，但只在 ownership 术语分层后兼容：

```text
未来跨进程真相（可选）: durable session + operation records
                               ↓ reduce/restore
当前进程内真相: Agent-owned complete NextTurnState
```

如果把 `Agent` 解释为跨进程最终事实源，则未来任何 durable restore 都会重新制造两个 owner；如果解释为 live runtime 的唯一 owner，则 session log 只负责重建，二者无冲突。

### 4.3 Session persistence

Opi 当前 session 是 append-only JSONL v1 conversation/metadata tree：`SessionEntry`、Leaf pointer、branch reconstruction、tail crash recovery；`SessionRepo` 只有 append/load/message_count，list/fork/directory policy 被明确留给 product。来源：[`opi-agent/src/session.rs`](../../crates/opi-agent/src/session.rs):1-41,220-289,350-436、[`opi-agent/src/harness.rs`](../../crates/opi-agent/src/harness.rs):258-278。

pi v4 SessionRepo 则已经包含 lane pointer、operation record、facts、global seq、bounded branch/log queries 与 open-operation recovery projection。两者不是同名等价物。当前 Opi 不应“升级接口以追平”——这会在没有 durable prompt、lane 或 remote service 消费者时，把 storage policy 与大量 orchestration schema提前放进 Agent Core。

真正值得保留的候选合同只有：

- accepted operation 与 durable record 的先后关系；
- live state 必须可由 durable prefix reduction；
- one-writer/fenced lease 与 corruption detection；
- intent-before-effect / result-after-effect；
- backend conformance across memory/file/database。

这些应在至少出现一个真实 durable operation 产品与第二个 storage/adapter 消费者后，通过单独 Phase + Placement Review 进入，而不是扩展现有窄 `SessionRepo`。

### 4.4 Observability and evidence

pi telemetry 是 passive diagnostic contract；Opi 规范要求的则是 resolved-execution evidence：stable run/turn/call correlation、finalized artifact reference、runtime/provider/wire/auth/fallback/policy/provenance，且 evidence completeness 会影响 authority。来源：[`docs/opi-spec.md`](../opi-spec.md):235-247。

当前 Opi 已有 `EvidenceSink`、typed identities、health、finalized manifest、noop/in-memory adapters，并且可信 tool authorizer 已开始接收 evidence-health generation；它比单纯复制 pi telemetry package 更接近 Opi 自己的规范目标。来源：[`evidence.rs`](../../crates/opi-agent/src/evidence.rs):38-159,180-218、[`authority.rs`](../../crates/opi-agent/src/authority.rs):1-26。

这里应借鉴 pi 的是“显式 context + no-op + conformance + exporter 在外”，而不是 package 拆分。Opi 当前只有 `opi-agent` 一个 domain owner，尚未证明需要 `opi-telemetry` 新 crate；先完成 evidence 在 agent loop 与 product adapter 的真实接线，才有第二消费者证据。

### 4.5 Evaluation

pi 的项目内 eval 验证了“用真实产品 harness、保存 native artifact、做 paired comparison”有实际价值；它支持 Opi 应尽快建立 measurable capability 的战略判断。

但 Opi 不应把 evals crate放进 workspace并依赖 `opi-coding-agent`：规范要求 Eval 是无 Opi crate 依赖、可评估 Opi/pi/其他 Agent 的 Independent Companion，Agent 与 grader 通过 process-capable adapters 接入。来源：[`docs/opi-spec.md`](../opi-spec.md):249-289,579-592。

## 5. 对 Opi 的调整建议

### 5.1 必须调整（当前收口，不新增拓扑）

| 项目 | 调整 | 验证 |
|---|---|---|
| Phase 17 evidence activation | 按既定顺序完成 evidence sink 在 agent loop、provider/tool/retry/compaction、finalization 与 product adapter 的真实接线；不要停在 schema/trait | 一次真实 mock run 产生完整 run/turn/call graph；required evidence failure 不能伪装为 complete |
| ownership 用语 | 把 `Agent` 的 “durable owner” 明确成 “sole in-process/live runtime owner”；为未来 restore 预留 `durable log → reduction → atomic replace` | 文档与测试能同时证明无 live duplicate owner、可从 persisted prefix 构建完整 state |
| 删除后的文档一致性 | 清理 `opi-agent::harness`、`CodingHarness` 中仍宣称未来接入 `AgentHarness` 的陈旧注释，保持与 README/API surface 一致 | `rg AgentHarness crates/` 只留下明确历史/删除说明，不再描述不存在的迁移目标 |
| protocol 命名边界 | 记录 `opi-protocol = command execution protocol`，未来 remote session proposal 必须另立 wire identity/placement | 无 remote-session DTO 混入 `command-execution-jsonl-v1` schema；proposal 单独通过 Placement Review |

这四项都不要求新增 crate，也不改变规范战略顺序。

| pi 信号 | Opi 应观察什么 | 进入条件 |
|---|---|---|
| v4 SessionRepo | operation record/reduction、bounded recovery query、writer fencing、backend conformance | 有真实 durable operation 产品；至少两个 storage/adapter；crash matrix 能机械验证 |
| protocol/client/server | authoritative snapshot、transient progress、lease ownership、structured errors、transport auth before bytes | 出现 remote Opi session 产品和第二个 client/transport；明确 threat model 与 backpressure |
| lanes | shared tree + isolated lane operation/queue state | Slack/thread、sub-Agent 或并行 workflow 成为真实产品需求并有 frozen Eval |
| telemetry package | explicit parent propagation、noop/in-memory adapter、conformance、no exporter in core | Evidence/diagnostic seam 出现第二个真实 crate/domain consumer，拆分能降低而非增加接口成本 |
| SQLite backend | materialized projections、bounded queries、fenced single writer | JSONL 已成为实际瓶颈，且 server/search 需求证明数据库生命周期差异 |
| pi evals | real-product harness、native artifacts、paired baseline/candidate、missing telemetry visible | 作为 Opi cross-Agent Eval 的 importer/adapter 证据，而非复制其 package placement |

### 5.3 不要跟随（当前明确拒绝）

1. **不要按 npm 目录复制 Rust crates。** Opi 规范明确不追求 pi package parity；新 crate 必须有稳定 seam 与真实消费者。来源：[`docs/opi-spec.md`](../opi-spec.md):89-94,104-117。
2. **不要恢复或扩张 broad `AgentHarness` 只为“方向一致”。** pi 自己的 public surface 是 compile-complete scaffold，promote export 不等于 runtime complete；Opi 删除未接入的第二状态 owner 是正确纠偏。
3. **不要现在把 lanes、manual drive、remote proxy、server、SQLite 全塞进 `opi-agent`。** 这些是一个完整产品路线，不是若干独立小 feature；没有 serving/product consumer 时会违反 deletion test。
4. **不要让 Opi Eval 依赖 `opi-coding-agent`。** pi-evals 适合项目内行为回归，不能替代跨 Agent、native grader、offline reproducible Evidence Producer。
5. **不要复用现有 `opi-protocol` 承载 remote session。** command execution 与 session control 的权限、生命周期、transport 和兼容性完全不同。
6. **不要把 pi telemetry 当作已经覆盖真实运行的证据。** 契约与 schemas 已实现，但 harness runtime 尚未发出完整 spans；Opi 也必须以真实 loop coverage 验收，而不是以类型存在验收。

## 6. 推荐决策

### 现在

- 保持六 crate workspace；不新增 `opi-client`、`opi-server`、`opi-session-backend-sqlite` 或 `opi-telemetry`。
- 继续 Phase 17 的深 Core 语义闭合，并完成上文三项文档/ownership 收口。
- 将本报告登记为 pi alignment evidence，不修改 normative spec：`STRAT-003` 已经明确规定 protocol/client/server/broad harness 继续观察。

### 下一次可以重开 Placement Review 的触发器

满足以下任一组真实证据时再重开：

1. **Remote session 组**：一个 Opi server 产品 + 两个真实 clients/transports + auth/backpressure/conformance；
2. **Durable harness 组**：一个 accepted-operation crash-resume 产品 + Memory/JSONL/SQLite 中至少两个 backends + effect-boundary crash matrix；
3. **Lane 组**：两个共享树但必须并行隔离 operation/queue 的真实 consumers；
4. **Telemetry split 组**：至少两个 crate 独立实现同一 adapter contract，且拆分能让 Agent Core 更小；
5. **SQLite 组**：JSONL 在 bounded query、writer fencing 或 inventory/search 上出现可测瓶颈。

### 最终判断

pi 0.84.1 确实在从“terminal coding agent monorepo”向“可远程服务、可持久恢复、可观测、可评估的 Agent platform”试探性扩张；其中 **session/storage foundation** 和 **protocol/client/server transport foundation** 是真实工程，不应被简单称为纸面设计。与此同时，决定平台价值的 **AgentHarness durable execution 与 coding-agent server assembly** 尚未落地，所以也不能把 package 数量当成完成度。

Opi 当前方向不需要转弯：Phase 17 在做的是这条未来路线所需的更小、更可信底层语义，而规范已经把 remote/broad harness 放在 observation 状态。最合适的调整是完成当前 Core 闭合、澄清 live/durable ownership、清理已删除 harness 的陈旧叙述；其余保持证据驱动，不追 package parity。
