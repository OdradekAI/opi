## Problem, goal and scope

Current `opi-ai` has route-selection, framing, terminal and producer-cleanup defects evidenced by historical probes. Its ordinary call composition, chronology, operation coverage, SDK-reachable authentication and public customization differ from Pi AI 1.3.0. Renaming symbols or reusing a few wire fixtures cannot establish equivalent caller behavior.

The goal is one independently usable Rust SDK: the same select/build model, provide context, stream/complete, inspect failure, append tool results, switch model, manage auth/catalog and release resources actions, with explicit language and correctness differences. Preserve known/unknown usage, secret-safe typed errors, owned call state and no implicit account fallback. No identical model output, JSON bytes, cache benefit, performance or billed-cost guarantee is made.

In scope:

- All 10 published built-in chat APIs, 1 image API, 4 classifier APIs, 42 built-in provider factories/profiles and 9 OAuth flow families in the pinned capability inventory, plus registered custom providers/APIs. Reused wires do not erase provider-specific auth/default/filter behavior.
- Models/provider management, operation-qualified model selection, custom complete records, native/simple four chat entry points, direct adapters, advanced prepare, final outcomes, timing, diagnostics and explicit cleanup.
- Model input Context/TranscriptContext, chronology/sections/tool changes, normalization, replay/opaque metadata, strict/grammar projection and public validation utilities. Tools remain declarations; callers execute them explicitly.
- Typed images/classification, classifier images where actually supported, pending/deferred fetch/cancel, explicit retry helpers, public header/payload/response/raw-event customization and model metadata/estimation/pricing/input limits.
- SDK-reachable API-key, OAuth and AWS/default-source mechanisms; injectable auth/store/presenter/clock/transport; catalog stores/refresh and explicit personalization. Construction performs no discovery or external I/O.
- Explicit telemetry-context propagation with host-owned domain instrumentation/backend; platform/package/CLI-helper alternatives and every observable Rust difference recorded in the current annexes.
- Necessary existing Rust caller adaptation caused by this SDK's scoped breaking changes, independent consumer/package acceptance and version-follow-up evidence.

Outside this package candidate: Agent execution/authorization/hook policy, durable session v3/child migration/compaction, product tool_search/UI/startup defaults, full MCP/codemode or virtual routing products, exporter/automatic domain-span schemas, unadopted Responses Lite, unverified real remote-deferred protocol, and speculative generic context/operation/plugin/transport frameworks. Host impacts remain traceable but do not become SDK completion gates. Dedicated OpenRouter Image API/image streaming are not delivered Pi 1.3.0 adapters and are not invented parity requirements. Native Rust support and TS/Bun/browser/CLI substitutions are explicitly bounded, not silently omitted capabilities.

## Actors and scenarios

1. An independent SDK caller builds a Models instance, registers built-ins or custom providers and selects or supplies a complete model record.
2. A caller uses native/simple stream/complete or advanced preparation and observes the same selected route and final message/failure.
3. A caller appends chronological instructions, declarations and actual tool results, serializes model input and changes provider without inventing authority or missing history.
4. A stream consumer sees stable event-time data and a single final outcome, and abandons work without leaking library-owned tasks.
5. A caller performs all published image/classifier operations, including model-qualified image input, and receives typed output, known accounting and protocol-specific failure.
6. An embedder supplies or manages authentication, observes atomic token rotation and provider-specific availability, and explicitly refreshes catalogs without hidden startup policy.
7. A continuing Codex caller chooses transport/cache behavior, keeps valid continuation and awaits instance-owned resource cleanup.
8. A caller explicitly selects whole-call recovery or resumes a deferred handle without automatic polling, tool execution or account switching.
9. A host passes its tracing parent through SDK operations without replacing a subscriber, exporting data or serializing backend objects.
10. A maintainer tracks upstream capabilities, plans and test changes against fixed source identities and distinguishes static review from executed acceptance.

## Responsibilities and owned state

| Owner | Responsibility | Boundary |
|---|---|---|
| opi-ai Models/catalog | Provider and operation-qualified records, atomic revisions, sole preparation and frozen call/variant/attempt state | Listing/configuration does not promise remote executability; no second model selection or account fallback |
| opi-ai adapters/runtime | Protocol compilation/parsing, effective compat/options, typed operations, timing and owned transport/continuation resources | No local tool execution or host session writer |
| opi-ai model context/validation | Context shorthand, canonical TranscriptContext, projection, schema conversion and public validation | Model input is serializable; request views preserve canonical facts and grant no authority |
| SDK auth sources/store | Injectable AuthContext, API/OAuth/AWS mechanisms, per-source state, serialized credential/metadata transactions | AuthContext is not model/trace context; no construction-time discovery, implicit login or concrete keychain dependency |
| opi-ai telemetry module / host | Explicit process-local parent plus source Dispatch / domain semantics, subscriber, sampling, export and flush | No automatic SDK domain spans, durable IDs, global backend or upload |
| SDK caller | Append messages/results, choose operation/retry/polling, store output and invoke cleanup | No implicit files, tool authority, hidden polling or product recovery |
| Existing Agent/product consumers | Adapt to scoped SDK API changes; preserve their own formal execution/session/permission contracts | Host-only AIR impacts neither authorize nor require new product/session policy |
| Research/document owners | Fixed capability inventory, differences, sole acceptance mapping and upstream evidence index | No parallel implementation ledger or automatic upstream adoption |

A logical call owns captured provider/model/input revisions and one selected auth/source binding; ordinary wire retries reuse them. Only one executable acquisition attempt is active. Trusted adapter adaptation may create at most the documented bounded payload variants, with immutable provenance per variant. It does not change account/model/provider, splice new output into a delivered stream or reset the variant/send budget.

Creation of a handle/Future captures owned inputs without I/O. First poll registers its resource generation before awaiting auth. Known structure is validated before auth; lawful auth endpoint/header material then determines endpoint-dependent compat, final validation and payload projection. Each payload variant runs onPayload once and freezes the post-transform payload for that variant's ordinary retries. Anthropic's specific strict-prefer downgrade is a bounded new variant, not arbitrary invalid-input retry. Functional callbacks and passive telemetry have different failure contracts.

The SDK is sessionless. It requires no Agent authorizer, durable transaction, child session, Promotion, host v3 writer or pre-dispatch durable acknowledgement. A durable host may consume frozen route/projection facts under its own admitted transaction contract; this candidate neither changes that contract nor installs a second writer. Caller generation never mutates Context, executes tools or starts product refresh/recovery.

Three context responsibilities remain separate: model Context/TranscriptContext (serializable input and normalization), AuthContext (injectable source access), and TelemetryContext (process-local observation). Construction/static reads perform zero env/store/auth/network work. Credentials/telemetry/runtime resources do not enter model serialization. See AIR-066 and the current annexes.

### Explicit telemetry context (Q37)

opi-ai owns a small telemetry module using the locked Rust tracing ecosystem. Do not add an opi-telemetry crate, generic backend trait/schema engine, OTel/Sentry dependency or default exporter in this target. Agent already depends on opi-ai and may use this mechanism without moving its domain or evidence types into the library. Host normal tracing/runtime dependencies are stated in standalone examples.

TelemetryContext::from_span(parent: tracing::Span) captures the source Dispatch from that Span, not the ambient default at a later poll; disabled/no source gives the explicit noop state. TelemetryContext::noop() is disabled; Clone retains the same parent/Dispatch and is Send+Sync. A host may explicitly pass Span::current(), but omission never captures it. Non-noop custom adapter instrumentation uses that explicit context/Dispatch; the SDK does not substitute a new call parent. Selected auth/management interfaces gain no automatic tracing requirement; a host can wrap their futures separately.

TelemetryContext::in_scope(FnOnce) executes the synchronous body exactly once under the captured parent/Dispatch and restores the caller context before returning; TelemetryContext::instrument(Future) preserves its output and lazy polling and applies the same context at poll/drop. Noop uses a disabled scoped dispatcher for these observation helpers, still executes business work once, and creates no spans or retention. This does not silence independent host logs or explicitly selected other contexts. These helpers create no domain names/status and do not drive a Future beyond caller polling; private Stream wrappers follow the same scoped rule.

This supplies pi-ai option integration, not source-level pi-telemetry utility compatibility. Native tracing has fixed callsite fields and no universal SpanStatus or callback-managed settlement. Domain instrumentation uses its own typed vocabulary, explicitly interprets Result/Stop/Length/Deferred/failure and finalizes its semantic scope once. Captured external native parents retain host-owned lifetime; SDK context cannot infer their semantic completion from Span clones. No generic startSpan wrapper or new Agent span families are required by this candidate.

Future instrument/with_subscriber alone does not cover a Stream or all Drop paths in tracing0.1.44. Private synchronous wrappers handle poll_next/drop and producer handoff under the captured Dispatch where observation is performed; never hold thread-local enter/default guards across await or drive extra business polls to record. Noop short-circuits this instrumentation rather than creating a root under an accidental ambient subscriber. An in-memory host/reference subscriber validates parentage and result preservation without external services; it is not a new production buffer/export API.
